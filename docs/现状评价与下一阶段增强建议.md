## 一、一句话结论

**这是一款「准生产级」的插件 —— 作为个人/团队自用，它已经在第一梯队；作为要上架集市的公共插件，它还差最后一层「产品化」。**

差距不在功能多少，而在三件事：**i18n 没接线、待办不能勾、命令面板显示的是英文标识符**。
前两件用户天天碰得到，第三件一按 `Ctrl+P` 就撞上。

## 三、做对了什么（这些是资产，重构时别弄丢）

1. **块是唯一真相源。** 导图不是一份独立数据，视图坏了数据也不会坏。这条决定了下限。
2. **让宿主的原生状态当唯一真相源。** 折叠态用思源原生 `fold`，不另存副本 ——
   跨设备、跨会话天然一致，还省掉一整套同步逻辑。
3. **「先给反馈，再等真相」。** 结构操作要写内核 → 内核回推 → 重挂视图，中间几百毫秒
   画面无变化。乐观占位 + 覆盖表都是同一个思路的两次应用。
4. **自建撤销栈 + 整块快照。** 块 API 写出的内容**天生不进思源的 Ctrl+Z**
   （实测四种块操作事务里 `undoOperations` 恒为空）。没有这一层，用户删错一个节点
   就是不可逆的数据丢失。快照还原只有一个代码路径，比逐操作求逆安全得多。
5. **验收方法论。** 首轮 11 项失败里只有 3 项是真 bug，其余是判据写错。
   「先用内省探针 dump DOM 真相，再决定改代码还是改判据」这条已经沉淀下来了。
6. **注释写「为什么」而不是「是什么」。** `history.ts` 开头把「为什么必须自己实现撤销」
   连同实测的事务字段都写进去了。这是 4220 行单体还能维护下去的唯一原因。

## 四、短板（按「用户能不能感觉到」分三层）

### A 层 · 用户直接能感觉到的

#### A1. 待办勾选是**纯装饰**，点不动

`renderer.ts:2424` 渲染出 `.mm-task` 的方框与 `✓`，但**没有任何点击处理**；
`MMActionKind` 里也没有 `toggleCheck`。

```
MMActionKind = insertChild | insertSiblingBefore | insertSiblingAfter | delete
             | indent | outdent | moveUp | moveDown | move | duplicate | paste
             | fold | unfold | locate | copy          ← 没有 toggleCheck
```

对一个明确支持「任务列表块」的插件，这是**最扎眼的功能缺口**：
用户能看到 `[x]` 和虚线连线（说明已完成），却必须退回大纲视图才能勾选。
批量场景更痛 —— 10 个待办要勾，得逐个回编辑器。

#### A2. 命令面板里显示的是英文标识符（已实测）

`Ctrl+P` 打开命令面板，看到的是：

```
大纲导图: migrateLegacy
大纲导图: toggleMindMap
大纲导图: toggleSidePanel
```

实测证据（`tests/kernel/probe-i18n-command.mjs`，只读）：

```json
{ "langKey": "migrateLegacy",   "resolved": "migrateLegacy",   "flatHit": false }
{ "langKey": "toggleMindMap",   "resolved": "toggleMindMap",   "flatHit": false }
{ "langKey": "toggleSidePanel", "resolved": "toggleSidePanel", "flatHit": false }
```

根因有两层，**都是可以一眼修掉的**：

1. 思源前端的解析式是**扁平查表** —— `a.langText || r.i18n[a.langKey] || a.langKey`，
   而 `i18n/zh_CN.json` 把文案**嵌套**在 `command` 下面（`command.migrateLegacy`），
   于是 `i18n["migrateLegacy"]` 是 `undefined`，直接落到 `langKey` 兜底。
2. `toggleMindMap` / `toggleSidePanel` 这两个 langKey **在 i18n 文件里根本不存在**。

#### A3. 插件自己的撤销栈只在导图内生效

`onHistory` 只在导图的 `onKeyDown` 里被调用。所以存在这个场景：
**在导图里删了节点 → 点一下编辑器 → 按 `Ctrl+Z` → 什么都没发生**
（思源的 undo 栈里没有这条记录，因为块 API 不写 `undoOperations`）。

这是设计取舍没错，但**用户不知道**。要么把插件的栈挂到更靠外的地方，
要么在删除类操作后给一句明确提示（「已删除 · `Ctrl+Z` 可撤销（需在导图内）」）。

#### A4. 搜索只覆盖当前这一张图

`searchHits` 只从当前 `tree` 里筛。且**不能按状态过滤** ——
「只看未完成的待办」这种需求在任务列表场景里非常高频，现在得靠肉眼。

#### A5. 没有「跨分支关系线」

这是成熟导图工具的标志性能力（XMind 的「联系」、MindNode 的 connection）。
现在只有父子连线，表达不了「分支 3 的某个节点依赖分支 7 的某个节点」。

### B 层 · 产品化（决定能不能上架 / 给外国人用）

#### B1. i18n 是**死代码**

```
i18n/zh_CN.json   11 个键
i18n/en_US.json   11 个键
src/ 里 this.i18n 引用次数：0
src/ 里含中文的字符串字面量：281 处（renderer 130 / index 80 / scanner 47 / theme 13 …）
```

也就是说：**除命令面板那 3 个（而且是坏的）以外，全部界面文案是硬编码中文。**
`en_US.json` 目前是纯粹的摆设。`plugin.json` 声明了 `frontends: ["all"]`、
`displayName.default` 是英文，一个英文用户装上去会看到一整套中文界面。

#### B2. `plugin.json` 还是占位符

```json
"author": "MindMap Plugin",
"url": "https://github.com/your-name/siyuan-plugin-mindmap",
"version": "0.1.0"
```

上架集市需要真实的作者名与仓库地址，`version` 也要开始按语义化版本走。

#### B3. 移动端只有「实现」，没有「适配」

有长按菜单、双指缩放、`touch-action: pan-y` 让纵向滚动交还页面 —— 说明作者是认真想过的。
但全 `src/` **没有一处 `isMobile` 分支**：工具条按钮尺寸、提示气泡、悬停类功能在触屏上
都没有降级路径。而且**一次真机都没跑过**（只在无头 Chromium 里验证）。

#### B4. README 有两处已经过期

| 位置 | 写的 | 实际 |
| --- | --- | --- |
| 第 146 行 | 设置里有「是否记忆折叠状态」开关 | 该设置项**已不存在**（折叠态走原生 `fold`，天然记忆） |
| 第 177 行 | 折叠状态写在块属性 `custom-mindmap-fold` 上 | 现在写**原生 `fold`**；`custom-mindmap-fold` 已降级为一次性迁移用的 `ATTR_LEGACY_FOLD` |

README 是集市详情页的内容源，过期描述会直接变成用户的错误认知。

#### B5. 未上架

`plugin.json` 齐了、图标预览图有了、README 双语有了、`package.zip` 能打出来。
差的就是上面 B1/B2 两件。

### C 层 · 工程（影响「还能走多远」）

#### C1. `renderer.ts` 4220 行 / 单类 190 个方法

占全部源码的 40.9%。里面混着：工具条构建、渲染、布局落位、连线绘制、键盘分发、
菜单、拖拽、触摸、小地图、导出准备、演示模式、预览卡片、幽灵占位……
**注释质量很高，所以现在还能读**，但再加两三个功能就会到临界点。

#### C2. 无障碍为零

`aria-*` 与 `role=` 在 `src/` 里命中数都是 **0**。
`.mm-root` 有 `tabindex=0`，键盘操作很完整 —— 但屏幕阅读器读到的是一个没有语义的 `div` 森林。
对一款「键盘优先」的应用来说，这是最容易补、收益最直接的一项。

#### C3. 触屏上「单选」没有可见入口

`renderer.ts:2584` 的注释写着：

> 顺带把「选中态常驻操作条」变成触屏上唯一的快捷入口

但**这个「常驻操作条」并不存在** —— 全项目搜不到 `.mm-actions` / `.mm-tools`。
批量条（`.mm-batch`）只在选中 **≥2** 个时出现。

结果：触屏上选中单个节点后，界面上没有任何可见的操作入口，
必须**知道**要长按才能呼出菜单。注释描述的是一个没被实现的方案。

#### C4. 没有诊断入口

用户遇到问题只能开控制台。没有「复制诊断信息」按钮，也没有版本 / 配置 / 节点数的一键导出。
排障全靠让他描述 —— 而这类问题往往一句话说不清。

#### C5. 收尾存在间歇性竞态（低概率）

整条 `ux:all` 跑完后，曾经有 **1 个**测试文档在十几分钟后重新出现
（`diag-canvas-v2` 的 docB，收尾明确调过 `removeDoc` 且返回 `code: 0`）。

已做过的排查：单跑 `diag-canvas-v2` 三次，每次跑完立刻看磁盘都是 **0 残留**；
受控实验（`probe-remove-open-doc.mjs`）证明「文档开在前端时删不掉」这个假设**不成立** ——
开着照样删得掉。所以只能定性为 `chrome.close()` 与内核落盘之间的**间歇竞态**，复现不了。

处置不追查，改**幂等**：整条回归跑完补一句 `npm run clean:tmp!` 兜底。

### P1-3 的难度评估（为什么不做）

方案里要求「先评估难度」。结论是**难度高**，理由不是「画线难」，而是**一致性难**：

1. 关系线必须持久化。存块属性就得跟着块走，于是**任何结构操作**（删除、移动、升降级、批量操作、
   撤销 / 重做、跨文档复制）都可能让一条线的某一端消失 —— 每一处都要接上「清理失效引用」。
2. 这条链路目前靠 `Ctrl+Z` 走插件自己的撤销栈（`HistoryEntry`），关系线会变成第二个需要快照的状态，
   和「块是唯一真相源」这条底线开始拉扯。
3. 本插件当前 12 支真机回归覆盖的是结构操作；引入关系线后这些用例的预期都要重新推一遍。

也就是说：**它能做，但它会把「一个小功能」变成「一次架构改动」**，而用户当前更缺的是 P0 / P1 里那几件
每天都会碰到的事。所以本轮明确跳过，留作长线。

### 补验 P2-5 时挖出来的一个真 bug（已修）

P2-5 的顶栏图标与两条带 hotkey 的命令上一轮就写完了，但只验过「顶栏图标存在」，
**没人真的按过那两个键**。补 `ux:cmds` 时按出来了：

> 导图**有焦点**时按全局切换键 `⌥⌘D`，会被导图自己的 `Ctrl+D`（复制节点）吃掉。

`renderer.ts` 的导图内快捷键只判 `mod = ctrlKey || metaKey`，没排除 `altKey`，
于是 `⌥⌘D` 命中「复制节点」分支，而该分支会 `preventDefault + stopPropagation` ——
**全局键根本没机会送达思源**。

实测后果（有对照实验，不是推断）：

| | 内核列表项数 | 导图 |
| --- | --- | --- |
| 修前 | 3 → **4**（静默复制了一份子树进笔记） | 仍开着（切换没生效） |
| 修后 | 3 → 3 | 切回大纲（全局键送达） |

**修法**：引入 `modOnly = mod && !e.altKey`，导图内所有 `Ctrl/Cmd + 单键` 快捷键改用它；
`Alt + 方向键`（升降级）也补上 `!mod`。这样 `⌥⌘` 整个命名空间让给思源与别的插件 ——
本工作空间里 flowmind 用 `⌥⌘K` / `⌥⌘L`、魔法排版用 `⌥⌘P`，它们本来也会被导图吃掉。

回归断言钉在 `ux:cmds` 的 D 段：**导图有焦点 + 有选中节点时按 `⌥⌘D`，
内核列表项数必须不变，且导图必须被切回大纲**。

## 六 · 收口阶段又挖出两个真 bug（第十九轮尾巴）

第十九轮的 P0 / P1 / P2-5 全部落地并验收之后，我按「有实现、没断言」这条线索
做了一遍自查，结果又挖出两件**会动用户数据 / 影响可用性**的事。两条都不是新功能，

### 6.1 `migrateLegacy` 是唯一会写数据的命令，动作从没被真机跑过

三条命令里它最危险（把 `custom-block-list-view="map"` 换成 `custom-mindmap`，
**写内核**），而此前只有一条「命令面板里标签显示中文」的断言。

排障时先要回答一个基础问题：**思源到底会不会把自定义块属性渲染到 `.list` 元素上？**
因为这条命令是 `document.querySelectorAll('.list[custom-block-list-view]')` ——
**从 DOM 读，不从内核查**。读不到的话，标签再漂亮也是死的。

探针 `probe-migrate-command.mjs` 的结论（真机，非推断）：

| 观测点 | 结果 |
| --- | --- |
| 内核写上 `custom-block-list-view="map"` 后 DOM | `.list` 上**确实有**这个属性（思源会贴） |
| 点命令后面板文案 | `大纲导图: 迁移【自定义块样式】的列表导图标记` |
| 迁移后 DOM | legacy 摘掉、`custom-mindmap="logic"` |
| 迁移后内核 | 同上（legacy 被清空） |
| 迁移后画面 | 导图**真的挂上了**（6 个节点 = 5 个列表项 + 虚拟根）→ `setTimeout(scanAll,150)` 生效 |
| 提示 | 「已迁移 **1** 个列表块」 |
| 反例：`custom-block-list-view="table"` | **原样保留**（设计意图：只迁移导图视图） |
| 再点一次 | 「没有找到来自【自定义块样式】的导图列表」—— 明确提示，不是静默 |

**三段耗时**（顺带量出来的，以后不用再猜）：
DOM 属性 **8ms** → 内核写入 **265ms** → 导图挂载 **266ms**。

> 这里踩过一个测量坑：`migrateLegacy` 是「**先** `list.setAttribute`，**再** `await setBlockAttrs`」，
> DOM 立刻变、内核稍后才写。第一版拿「DOM 已经变了」当「内核已经写了」的证据，
> 于是内核那两条断言假红。**DOM 变 ≠ 内核变**，必须分开等。

### 6.2 ★ 真实键盘下导图的整套 Ctrl 快捷键是失灵的

这个是本轮最值钱的发现，也是最难发现的。

**现象**：导图开着、节点选中、焦点在 `.mm-root`，用**真实键盘的顺序**按 `Ctrl+D`
（先产生 `key === "Control"` 的 keydown，再产生 `D`）—— 「复制节点」不生效，
内核列表项数 3 → 3。

**机制**：裸修饰键那一下导图没有任何动作可做（不会 `preventDefault`），
可思源的编辑器照样在这个 keydown 里 focus 自己 —— 焦点被抢到 `.protyle-wysiwyg`，
而它**是 `.mm-root` 的祖先**。于是紧接着的 `D` 那一下 `e.target` 已经不在导图里，
`handleGlobalKey` 开头 `if (!this.rootEl.contains(t)) return` 直接返回。

| 发法 | 焦点 | 内核列表项数 | 插件收到？ |
| --- | --- | --- | --- |
| 真键盘式 `Ctrl+D`（先 ControlLeft） | mm-root → **protyle-wysiwyg** | 3 → 3 | ❌ |
| 单事件 `Ctrl+D`（只发字母 + modifiers 位） | mm-root → mm-txt | 3 → 4 | ✅ |

**为什么一直没被发现**：`tests/` 里所有键盘用例用的都是**单事件**发法
（`page.press` 那一路：一次 `rawKeyDown` + `modifiers` 位）。这种发法**没有裸修饰键那一下**，
焦点不会丢 —— 测试全绿，真实用户按 `Ctrl+D` 却没反应。整套 `Ctrl+A/C/V/X/D`
以及缩放那几个都一样。

**修复**（`src/core/renderer.ts`）：

1. `handleGlobalKey` 里除了「被我们接管了就抢回焦点」，**修饰键单独按下那一下也要抢**：
   `if (e.defaultPrevented) this.restoreFocus(); else if (MODIFIER_ONLY_KEYS.has(e.key)) this.restoreFocus(true);`
2. `restoreFocus(true)` 再多补两次（60ms / 200ms）—— 实测思源编辑器抢焦点**有快有慢**，
   只做一次 `setTimeout(0)` 会输给「晚一个节拍」的那种。
   补的两次**必须收窄**到「焦点确实落在 `.protyle-wysiwyg` 里」，
   否则按 `⌥⇧P` 时会把焦点从刚打开的命令面板输入框里抢回导图，用户就打不了字了。

**还有一个「假红」的坑**：第一版 `combo()` 把「按下 Ctrl」和「按下 D」**零间隔**连发，
比真人快得多，字母键比异步抢焦点还早到 —— 修复后仍然时红时绿。
真人会按住 Ctrl 几十毫秒才按字母，补上 `gap`（130ms）之后：
**修复版稳定绿（3 → 4），撤掉修复稳定红（3 → 3）**。

### 6.3 两条判据都做了「能红」验证

按本项目的纪律，新断言必须先被证明**能红**，否则只是装饰：

| 判据 | 怎么让它红 | 红的时候长什么样 |
| --- | --- | --- |
| `⌥⌘` 通用规则（G 段） | 把 `modOnly` 改回 `mod` | `⌥⌘A` → `.mm-multi` 0→2、`⌥⌘C` → 剪贴板 0→1、**`⌥⌘X` → 内核 3→2** |
| 真实键盘式 Ctrl（H 段） | 注释掉 `MODIFIER_ONLY_KEYS` 分支 | 内核 3 → 3，焦点 mm-root → protyle-wysiwyg |

G 段第一版还翻过一次车：拿「补发裸修饰键」的 `combo()` 去测「导图会不会误吃 ⌥⌘X」，

## 七 · 把「有实现、没断言」从碰运气变成扫一遍（第二十轮）

### 7.1 为什么这一轮值得做

第十九轮末尾挖出的两个真 bug（`migrateLegacy` 从没跑过、真实键盘下 Ctrl 快捷键失灵）
有个共同点：**都是「碰巧想到」才去查的**。碰巧这件事不能当流程用。

所以这一轮不再逐条想「还有什么没测」，而是把它变成一次**静态扫描**：
把插件的**全部用户可见入口**从源码里枚举出来，逐条对照 `tests/` 的命中情况，
产出缺口清单，再对真缺口补断言。

### 7.2 做法：`scripts/coverage-audit.mjs`

入口不从记忆里列，从源码里抠：

| 入口类别 | 从哪枚举 | 条数 |
| --- | --- | --- |
| 命令 | `addCommand({ langKey })` | 3 |
| 块菜单 / 顶栏菜单 | `IMenu[]` 里的 `label:` | 4 |
| 设置面板 | `addToggle / addSelect / addNumber / addText / addItem({ title })` | 24（正则）／**25（面板实测）** |
| 导图内快捷键 | `SHORTCUT_HELP` | 13 |

> 两个条数不一样本身就是一条信息：**机械枚举会漏**。设置面板的 25 项以探针实测为准
> （`probe-settings-effects.mjs` 里打开真面板数出来的），脚本的 24 项说明有 1 项
> 的写法没被正则覆盖。所以脚本的定位是**找线索**，不是下结论 ——
> 文件头也写明了：静态 grep 只说明「这个字串没在测试里出现过」，

`npm run audit:coverage` 可直接跑。

按模块算，连线是「测过的」；按入口算，它是零覆盖。

| `lazyRender` | `data-mm-lazy="1"` + 无 `.mm-root` | 见 7.5 第 1 条 |
| `edge` | `.mm-edges path` 的条数与 `d` 命令 | 直线 5 条 / 折线 9 条 / 曲线含 `Q`（9 条里 5 条） |

### 7.5 三个「信号找错了」的坑（都花了不止一轮）

1. **`hardLimit` 有两层拦截，不是一层。**
   第一层是明摆着的：`mount()` 只在**首次挂载**时判上限，改 config + `refreshAll()`
   对已挂载的列表无效 —— 必须用一个**从没挂载过**的列表。
   第二层是隐藏的：`lazyRender` 默认 **true**，`scan()` 里有
   `if (opts.lazyRender && !this.visible.has(id)) { observeLazy(list); continue; }`。
   专门预留的那个列表在文档底部、从没进过视口 → 永远不在 `visible` 里
   → **scan 根本没走到 `mount()`**，上限判定一次都没执行。
   现象是「探针里一切正常，就是没有提示」，非常像功能坏了。
   修法是连 `lazyRender: false` 一起临时关掉。
2. **`hoverPreview` 的悬停目标是珠子，不是节点。**
   `armPreview` 绑的是 `tog.onmouseenter`（`renderer.ts:2842`），
   不是整个 `.mm-node` 的 mouseenter。悬停节点中心 → 珠子收不到事件 → 永远没有卡片。
3. **靠鼠标点珠子来折叠，在长链路里会静默落空。**
   `flipAnimation` 那一项前后试了三轮都是 0：
   先是以为它是 CSS transition（看错了信号），再是怀疑 headless 的
   `prefers-reduced-motion` 是 `reduce`（实测 **false**，显式模拟 `no-preference` 也没用）。
   真因是**那一步的折叠压根没发生** —— 前面的步骤滚过页面、悬停过，
   按算出来的坐标去点，点空了，而点空**不报错**，只是「没折成」。
   改成程序化 `view.toggleFold(n)` + 给 `detachVanishing` / `runCollapse`
   包一层计数器之后：`.mm-collapsing` 峰值 **0 → 6**，计数器 `detach=[3,3,3,3]`。
   **这一项不是 bug，是探针的锅** —— 但它差点被记成一个「布局动效无效」的假 bug。

另外两个小坑：`viewSummaries()` 返回 `{ where, info }`，**没有 `id` 字段**（要按 `where` 匹配）；
`markdown` fixture 里两个列表之间**必须夹一个段落**，否则 Lute 会把它们合并成一个列表块
（`- 懒甲/乙/丙` + `- 上限甲/乙/丙` 变成 1 个 6 项列表，`kids()` 只数得出 3 个列表）。

### 7.6 「能红」是怎么保证的

这一轮 **35 条断言**里，绝大多数**自带反例**：同一个 run 里先量「关」再量「开」，
两次数值不同才算过。功能要是坏的，「开」就会长得跟「关」一样 → 断言自己就红了。
这比「改源码 → 重打包 → 确认变红 → 改回来」更省事，而且**反例是常驻的**。

唯一没有自带反例的是 `hardLimit`（上限判定只在首次挂载时走，一个列表只能验一次），
所以它靠「点『仍然渲染』之后 `.mm-notice` 消失 + 节点出现」来证明
那个提示**真的在拦渲染**，而不是一个装饰性的 div。

此外仍按项目纪律做了一次真破坏对照：把
`const vanish = oldTree && this.options.flipAnimation ? … : []` 改成 `const vanish = [];`
→ build + deploy → 跑断言：

```

  ✗ 开：detachVanishing 确实摘出了要消失的节点  计数器 {"detach":[],"collapse":[]}
```

**只有 E 段那两条「开」的断言变红，其余 26 条保持绿** —— 说明断言精确地钉在
它该钉的地方，不是装饰。还原后复跑 **35 / 35**。

### 8.4 ★ 扩面扫出来的真 bug：`导出 PNG` 与 `复制为图片到剪贴板` 全线失败

这是本轮最值钱的发现，也是「把审计面扩到自绘 UI」的直接收益。

**现象**：`导出 PNG` 点下去，**什么都不产出**，只有一个 4 秒的「导出失败」提示。

**抓到的插件自己的报错**（`probe-png-export.mjs` ② 段）：

```
[mindmap] 导出失败 Failed to execute 'toBlob' on 'HTMLCanvasElement':
  Tainted canvases may not be exported.
snackbar: "导出失败"
```

**为什么一直没被发现**：`diag-canvas-v2.mjs` 的导出段原来只有两条断言 ——
「导出菜单里有『导出 Markdown 大纲』」「导出菜单里有『复制为图片到剪贴板』」。
**只验了菜单里有没有这两个字，导出链路一次都没跑过。**

**根因**（最小对照，不是推断）。同一份 SVG，只换「图片源」：

| 图片源 | 结果 |
| --- | --- |
| `blob:` URL | ❌ `toBlob` 抛 `SecurityError`（画布被判定污染） |
| `data:` URL（encodeURIComponent） | ✓ 正常产出 601 字节 |
| `data:` URL（base64） | ✓ 正常产出 601 字节 |

内容维度的对照（都用 blob URL）：

| SVG 内容 | 结果 |
| --- | --- |
| 纯 `<rect>` | ✓ 350 字节 |
| `<text>` 元素 | ✓ 640 字节 |
| **`<foreignObject>`（120×60、一行文字）** | ❌ **污染** |
| `@font-face` 相对 `url(...)` | ✓ 352 字节 |

所以：**Chromium 把「SVG 当图片加载」时，只要 SVG 里含 `<foreignObject>`，
画布就会被判定为被跨源数据污染**，`toBlob` / `getImageData` 全部抛 `SecurityError`。
与内容无关（120×60 的最小复现同样触发）、与主题 / 图片 / 字体无关、
与无头 / GPU 也无关（这是安全判定，不是渲染判定）。

而 `buildSvg` 的节点层**正是用 `<foreignObject>` 包的**（为了让导出的文件
脱离思源也能还原外观）—— 于是 PNG 这条路必死。

**修复**（`src/core/exporter.ts` 的 `renderPngBlob`）：把图片源从 blob URL 换成 data URL。
**一行**：

```ts
// 之前：const url = URL.createObjectURL(new Blob([svg], { type: "image/svg+xml;charset=utf-8" }));
const img = await loadImage("data:image/svg+xml;charset=utf-8," + encodeURIComponent(svg));
```

用 `encodeURIComponent` 而不是 base64：少一次 `btoa` 的开销，而且 SVG 里有中文节点文字，
直接 `btoa` 会抛 `InvalidCharacterError`。

**修复后验证**：

```
点「导出 PNG」： clicked
下载文件名： ["临时-导出PNG-….png"]
抓到的 Blob： [{"type":"image/png","size":26202,"kind":"png"}]
console.warn： []
snackbar： ""          ← 不再有「导出失败」
```

`exportSvg` 不受影响（它走下载，不经过 canvas，blob URL 没问题）。

### 8.5 顺带修掉两条我自己写错的断言

补断言的过程中有两条**假红**，都是断言写错而不是功能错：

1. **「SVG 里带着节点文字」** —— 取文字时直接 `replace(/<[^>]*>/g)`，
   而 SVG 开头内联了整份 `PLUGIN_CSS`（几十 KB），于是取到的全是 CSS 文本。
   修法：先把 `<style>…</style>` 剥掉再取。
2. **「导出 Markdown 大纲以 `#` 开头」** —— `outlineMarkdown()` 的产物是**纯大纲**
   （只有列表项，标题只用来当文件名）。改成断言「首行是 `- `」+「保留了层级缩进」。

这两条记在这里，是因为它们说明一件事：**补断言时，「红了」先要怀疑断言自己**。

## 九 · 追那条红断言，又追出第 5 个真 bug：高清导出从来没高清过

### 9.1 那条红断言的根因：**是我的断言写错了**

上一轮 `diag-canvas-v2.mjs` 收尾时留下一条红：

```
✗ 只导出选中：裁剪后的画布不大于全图  undefined×undefined ≤ 907×489
```

`cropped` 是 `undefined`，说明没抓到 SVG Blob。当时的怀疑方向是「菜单项没点到」
或「选中态被清了」。**都不是**。真因在 `renderer.ts:1231`：

```ts
click: () => void this.doExport("png", this.selectedInDocOrder()),
```

「只导出选中」走的是 **`"png"`**，产物是 **PNG**。而我的断言写的是
`dlCrop.blobs.find((b) => b.isSvg)` —— 在 PNG 里找 SVG，永远是 `undefined`。

这是本轮第 3 条「红了先怀疑断言自己」的实例（前两条见 8.5）。
修法两处：

1. 产物找 `isPng`；
2. **PNG 的尺寸要从 IHDR 里读出来** —— 8 字节签名 + 4 字节块长 + 4 字节 `IHDR`，
   紧跟 4 字节宽 + 4 字节高（大端）。不读这个，「2 倍导出」这类问题就永远验不了
   （魔数只能证明「它是个 PNG」）。

顺带把断言从「不超过全图」加强成两条：一条「不超过」，一条**「至少一个方向严格更小」**。
后者是必须的 —— 只写「不超过」的话，少传一个 `crop` 参数退化成「偷偷导了全图」，
断言照样通过。

### 9.2 ★ 加了尺寸断言之后，第 5 个真 bug 当场现形

刚把 IHDR 读出来，第一条就红了：

```
✗ 导出 PNG 是 2 倍分辨率（高清导出真的高清）  907×489 vs 期望 1814×978
```

而 `renderPngBlob` 的签名是 `(rootEl, scale = 2, crop?)`，
`exportPng(this.rootEl, this.title, 2, crop)` 也**明确传了 2**。根因在 `exporter.ts:264`：

```ts
const s = Math.min(scale, maxSide / Math.max(W, H), 1);
//                                             ↑ 这个 1
```

尾部那个 `1` 把倍率封死在 **≤ 1**，于是 `scale` 参数彻底成了摆设 ——
**两个调用点都传 2，导出的 PNG 却永远和画布 1:1**。
`复制为图片到剪贴板`（`renderPngBlob(this.rootEl)` 走默认值 2）同样中招。

它和 8.4 那个污染 bug 是**同一个缺陷类别**：不报错、魔数正常、体积正常、
`console` 干净 —— 没有任何一条既有断言能碰到它。区别只在于
8.4 是「整条链路断掉」（还能靠真机点一次发现），
而这一个是**静默降级**（导出成功、只是不清真），
不把产物尺寸量出来就永远发现不了。

`git log -S` 显示这个 `1` 从最初提交（`2a37058 chushi`）就在，不是后来改坏的。

**修法**（一行）：

```ts
const s = Math.min(scale, maxSide / Math.max(W, H));   // 去掉尾部那个 1
```

`maxSide = 8192` 的钳制保留 —— 它管的是「画布超上限会静默变空白」，与倍率无关。

### 9.3 修之前先回答「值不值得修」：2 倍到底是重新光栅化，还是把位图放大？

这是个**渲染质量**问题，不能靠推断。如果 Chromium 是把 SVG 按固有尺寸光栅化、
再把那张位图放大，那 2 倍只是「变大」而不是「变清晰」，修了也没意义。

给 `probe-png-export.mjs` 加了第 ⑥ 段做像素级对照：同一份 SVG，
A = 直接画进 2 倍画布；B = 先画 1 倍、再把那张位图放大到 2 倍。逐像素比：

| 指标 | A（重新光栅化） | B（放大位图） |
| --- | --- | --- |
| 与对方的像素差异 | 3.70% 的像素不同 | 3.70% 的像素不同 |
| 清晰度（灰度梯度均值，越大越锐） | **1.463** | 1.201 |
| PNG 体积 | 72 KB | 80 KB |

**结论：① 按目标尺寸重新光栅化** —— 2 倍是真的更清晰（锐 22%），值得修。
肉眼也确认了：`tests/.build/probe-png-sharp-cmp.png`（上 A 下 B 的对照条），
A 的连线是干净的一条细线，B 明显发虚带晕。

## 十 · 零命中清单里最像真缺口的那条，果然是真缺口：`恢复本列表的默认视图`

### 10.1 从「零命中」到「真 bug」只差一次静态读码

8.7 里留了一句：「`恢复本列表的默认视图`（`forgetPref` + `applyViewPrefs({})`）
是其中最像真缺口的一个」。这一轮把它验了 —— 确实是真 bug。

它的原实现（`renderer.ts:1005`）：

```ts
click: () => {
    for (const k of Object.keys(this.prefs) as Array<keyof MMViewPrefs>) this.forgetPref(k);
    this.applyViewPrefs({});
    this.render(true);
    showMessage("已恢复默认视图", 2000);
},
```

而 `applyViewPrefs` 的语义是「用偏好**覆盖**全局默认」，所以它逐项写的是

```ts
if (prefs.layout) this.options.layout = prefs.layout;
if (prefs.theme) this.options.theme = prefs.theme;
if (prefs.edge) this.options.edge = prefs.edge;
```

**只覆盖「显式给出」的项。传空对象进去，一项都不覆盖。**

于是：

| 步骤 | 结果 |
| --- | --- |
| `forgetPref(k)` 逐个 | `prefs` 清空 ✓，块属性防抖 420ms 后整个删掉 ✓ |
| `applyViewPrefs({})` | `options.layout / theme / edge` **纹丝不动** ✗ |
| `render(true)` | 画出来还是旧布局 ✗ |
| `showMessage("已恢复默认视图")` | **弹了一个说谎的 toast** ✗ |

也就是：**块属性里确实清干净了**（下次打开这个列表会回到默认），
但**当前画面一点变化都没有**。用户点完看到「已恢复默认视图」，
盯着屏幕等它变 —— 什么都没发生。

> 「会说谎的提示」比「什么都不做」更糟：前者会让用户以为是自己看错了。

### 10.2 判据必须盯**画面**，不能盯 toast

这条之所以能藏住，是因为它**长得很像成功**：toast 弹了、块属性清了、
`console` 干净、没有任何报错。只断言「点了之后 toast 出现」或
「块属性被删掉」，两条都会稳稳地绿。

钉住它的是这三条（加在 `diag-canvas-v2.mjs` 第 [3] 段）：

```js
ok(segBefore3b === "mind" && !!a3b, "（前置）先把布局改成 mind 并等偏好落盘", …);
ok(segAfter3b === "logic", "★ 点完之后画面真的回到了全局默认布局（不是只弹个 toast）",
   `mind → ${segAfter3b}｜期望 logic`);
ok(!String(a3bAfter || "").includes("layout=mind"), "块属性里的 layout 偏好也被清掉了", …);
```

关键在中间那条：**盯分段控件的高亮**（`seg`），也就是盯「用户眼睛看到的东西」。
`STATE` 里的 `seg` 是从 `.mm-seg button.mm-on[data-layout]` 读的，
它由 `syncToolbar()` 按 `options.layout` 同步 —— 正好卡在坏掉的那一环上。

### 10.3 修法：把「撤掉覆盖层」这半个动作补上

新增 `resetToGlobal()`，并在 `setOptions()` 里同步「全局默认」快照
（用户在设置面板改了全局主题后，「恢复默认」要回到**新的**全局默认）：

```ts
private globalDefaults: { layout: MMLayout; theme: MMThemeId; edge: MMEdgeStyle };

setOptions(options: Partial<MMConfig>) {
    if (options.layout) this.globalDefaults.layout = options.layout;
    if (options.theme) this.globalDefaults.theme = options.theme;
    if (options.edge) this.globalDefaults.edge = options.edge;
    Object.assign(this.options, options);
    …
}

private resetToGlobal() {
    this.prefs = {};
    this.prefsDirty.clear();
    this.options.layout = this.globalDefaults.layout;
    this.options.theme = this.globalDefaults.theme;
    this.options.edge = this.globalDefaults.edge;
    this.syncToolbar();
    this.render(true);   // fitView：记住的缩放也一并作废，重新取景才是「默认视图」
}
```

菜单项改成「① 清偏好 + 通知落盘 → ② `resetToGlobal()` → ③ toast」。
第 4 个偏好键 `scale`（记住的缩放）由 `render(true)` 的 fitView 顺手处理掉。

**`applyViewPrefs` 本身没错**，它的语义就该是「只覆盖显式项」——
错在「恢复默认」这个**动作**少了一半：它既要清掉覆盖，也要把覆盖层撤掉。

## 十一 · 设置面板的「改 / 存盘 / 重启 / 取消」四条链路

### 11.1 这条缺口挂了四轮

从 7.8 到 10.6，每一轮的「还没做的」里都有这一条：

> 设置项的「存盘 / 读回」链路：已验「改内存 config → 行为变了」，
> 未验「点设置 → 存进 conf.json → 重启还在」。

它比前面几条更难验 —— 要**点三层设置 UI**（顶栏图标 → 菜单「设置」→ 面板里的控件），
而本项目在 2043 行附近恰好写过一条相反的经验：
「给『瞬态 / 无 UI 入口』的功能补断言时，别去点三层设置 UI（直接改内存 config 再调 `refreshAll`）」。

那条经验在这里**不适用** —— 因为要验的恰恰就是那条 UI 路径本身。
（这也是个教训：**「别点三层 UI」是省事的手段，不是目的；目的就是 UI 本身时不能省。**）

### 11.2 三个实测踩出来的坑（省得下次再踩）

| 坑 | 真相 |
| --- | --- |
| 配置文件路径 | `saveData("config")` 落点是 `<ws>/data/storage/petal/<插件名>/config`，**没有 `.json` 后缀**。按同目录下别的插件的 `script.json` 类推 → 明明存盘成功却报「磁盘上没有 config.json」 |
| 面板条目标题 | 标题在 **`.config-name`**；`.b3-label__text` 里装的是**描述**。按描述找会 `no-label` |
| 底部按钮文案 | 是「**保存**」不是「确定」（`b3-button--text`）；取消是 `b3-button--cancel` |

顺带一个 JS 层面的小坑：在 `page.eval` 的**模板字符串**里写注释时不能用反引号 ——
内层反引号会把外层模板提前截断（本轮踩了两次，报 `missing ) after argument list`）。

### 11.3 实测：两条是好的，一条是坏的

实现是这样的（`index.ts`）：

```ts
const addToggle = (…, changed) => { … box.onchange = () => changed(box.checked); };
// 每个 changed 都只写内存：
addToggle("小地图", …, (v) => { this.config.minimap = v; });
// 落盘只发生在「保存」：
new Setting({ confirmCallback: () => { void this.saveConfig(); this.scanner.refreshAll(); } });
```

四条链路实测结果：

| 链路 | 结果 |
| --- | --- |
| ① 改开关 → 内存变了 | ✓（已有断言验过） |
| ② 点「保存」→ 写进磁盘 | ✓ 磁盘上真的出现 `config`，值正确 |
| ③ 重启 → 从磁盘读回 | ✓ 重载页面后 `config` 等于磁盘上的值 |
| ④ 点「取消」→ 应该不生效 | ✗ **取消只取消了落盘，没取消内存改动** |

④ 的后果：用户改了开关、点「取消」、以为没改；但 `this.config` 已经被改了，
**下一次任何重渲染（编辑一下文档、切个文档）那个开关就悄悄生效了**；再重启又回去。

> 又是一个「只说了一半真话的按钮」。和第十节那个 `恢复本列表的默认视图` 是**同一个家族**：
> **动作只做了一半** —— 那边是「清了记录没撤效果」，这边是「撤了落盘没撤内存」。

### 11.4 ★ 又踩了一次「基线取错导致假绿」（本项目第 4 次）

第一版判据写的是「取消后内存 == **原始默认值**」：

```js
ok(memAfterCancel === p0.minimap, "取消把内存回退了");   // ← 基线取错
```

可前一步刚好把开关点回了原始值，于是「取消后 == 原始值」**必然成立** ——
断言报绿，把「取消根本不回退」这个事实完整地盖住了。

**基线必须是「点这一下之前的内存值」**，而且还要额外钉一条
「点完之后草稿值确实和基线不同」，否则下一条断言照样可能是假绿：

```js
const baseMem = await memMinimap();          // ← 点之前
await flip();
const draftValue = await boxChecked();
ok(draftValue !== baseMem, "草稿确实和真实配置不同（否则下面几条会假绿）");
```

修前实测（改回直写时的「能红」输出）：
`✗ ★ 取消之后真实配置仍是原值（草稿被丢弃）  true → false` —— 这才是真相。

### 11.5 修法：草稿模型

SiYuan 的 `Setting` 只有 `confirmCallback` / `destroyCallback`，**没有 `cancelCallback`**，
所以「在取消时回滚」这条路走不通。改成**草稿模型**之后，取消天然正确：

```ts
const draft: MMConfig = { ...this.config };
const setting = new Setting({
    confirmCallback: () => {
        this.config = { ...draft };      // 点保存才落到真实配置
        void this.saveConfig();
        this.scanner.refreshAll();
    },
});
// 21 处回调（18 个 toggle/number/text + 3 个 select）全部改成写 draft
```

`cancel` 时草稿被丢弃，`this.config` 从头到尾没被碰过 —— **不需要任何钩子**。
顺带的好处：面板改动不再「半生效」，语义变干净 —— 要么点保存整体生效，要么点取消整体不生效。

⚠️ 21 处里前 18 处是 `= v;`，后 3 处（layout / edge / theme 三个 select）是
`= v as MMLayout;`。第一遍只替换了 `= v;` 那种，**漏了带类型断言的 3 处** ——
用正则批量改时，先 grep 一遍「所有赋值形态」再动手。

### 11.6 草稿模型的一个副作用（写测试时会撞上）

草稿模型下点「保存」是 `this.config = { ...draft }` —— **整体覆盖**。
所以测试里如果想「直写 `p.config.X` 再点保存」，那个直写会被草稿冲掉。
必须**通过面板**把控件拨到目标值。实测踩过：第 E 段第一版直写 config，
结果磁盘上还是旧值，报红。

## 十二 · 收口时的最后一条红灯：取景钳制按「画布」算，白白浪费一份内边距

**第 8 个真 bug。** 发现方式是「跑整套回归时冒出来一条稳定红」——
它不在零命中清单上，也不在审计报告里，是 `ux:all` 自己报出来的。

### 12.1 现象

`ux:all`（16 支）第一支就挂，而且连跑三次数字**完全相同**（稳定复现，非偶发）：

```
✗ 可读优先取景不浪费可视区  内容 1231px ≥ 视口 519px，覆盖率 87.0%（应 ≥90%）
```

### 12.2 先排除三件事

| 怀疑 | 实测 |
| --- | --- |
| 部署件与源码不一致 | `cmp` 一致 ✓ |
| 磁盘配置被前几轮探针改坏 | 与 `DEFAULT_CONFIG` 逐字段一致 ✓ |
| `--window-size` 在 `--headless=new` 下没生效 | 实测 `innerWidth = 1664` —— **是生效的** ✓ |

第三条值得单独记一笔：`--window-size` 在 `--headless=new` 下**确实生效**，
别再往这个方向怀疑。519px 是**思源文档区**的宽度，不是窗口宽度。

### 12.3 把数字拆开

断言量的是「可见节点包围盒」对可视区的覆盖率：`内容 1231px` / `视口 519px` / `左空 68px`。

而 `render()` 里：

```ts
const box = layout(root, { mode, gapX, gapY, padX: 72, padY: 64, maxCross });
```

`layout.ts` 里 `box.w = maxX - minX + padX * 2`，于是：

```
worldW 2381 = 内容 2238 + 72 × 2      （实测 worldW = 2381，2238 = 1231 ÷ 0.55）
```

缩放 0.55 下，画布内边距 = 72 × 0.55 = **39.6px**。而：

```
68 ≈ 28 + 39.6
```

前半 `28` 是 `frameAxis` 的最小留白常量 `M`，后半 `39.6` 就是**画布内边距**。

### 12.4 根因

```ts
private frameAxis(want: number, c: number, v: number): number {
    const M = 28;
    if (c <= v - M * 2) return (v - c) / 2;
    return Math.min(M, Math.max(v - c - M, want));   // ← 钳的是画布边缘
}
```

`fit()` 传进来的 `c = worldW × scale` 是**画布**宽，于是钳制把**画布左边缘**钉在 28px 处。
可用户看到的是**内容** —— 内容在画布内侧还缩进着 39.6px，左空就变成了 68px；
右侧对称地也多空一份。内容宽 1231px、视口 519px 时：

```
覆盖率 = (519 - 68) / 519 = 87.0%
```

白白浪费 136px（左右各 68px），占可视区 **26%**。

### 12.5 修法

给 `frameAxis` 加第四个参数 `pad`（已乘缩放），把「装不装得下」的判断和钳制目标
都改用**内容边缘**：

```ts
const content = c - pad * 2;
if (content <= v - M * 2) return (v - c) / 2;
return Math.min(M - pad, Math.max(v - c + pad - M, want));
```

`pad` 的来源是 `render()` 里那两个字面量 —— 提成模块常量 `LAYOUT_PAD_X / LAYOUT_PAD_Y`
让两处共用（否则改一处忘一处，下次又对不上）。

修后：

```
✓ 可读优先取景不浪费可视区  内容 1231px ≥ 视口 519px，覆盖率 94.6%（应 ≥90%）
                            ｜画布 1310px、左空 28px（其中画布内边距占 40px）
```

那条诊断里的「画布内边距占 40px」正是 72 × 0.55 —— 与推算吻合到 1px。
（诊断字段本身就是这次顺手加进断言的：**断言失败时必须能自己说清差在哪**。）

⚠️ 三处调用点都要传 `pad`：`fit()` 的 x/y 两个轴、`applyRememberedScale()` 的 x/y 两个轴。
**漏一处就是半个修复** —— 而「恢复上次缩放」那条路径平时跑不到，漏了也不会立刻红。

### 12.6 为什么它之前是绿的

同一个 68px **绝对**空白，在不同视口宽度下的**占比**完全不同：

| 视口宽 | 覆盖率 | 判定 |
| --- | --- | --- |
| 519px | 87.0% | ✗ |
| 1100px | 93.8% | ✓ |

这条断言量的是**比例**，缺陷是**绝对像素** —— 于是「文档区变窄」这种纯环境变化，
会让一条正确的老断言突然变红。**这时候最容易做的错事是去调阈值。**

正确的做法是把它拆开算：`68 = 28 + 39.6`，看到 `39.6` 就等于看到了 `padX × scale`，
根因自己就浮出来了。**断言红了先算数，再决定是改代码还是改阈值。**

### 12.7 不是本轮引入的

```
git show HEAD:src/core/renderer.ts | grep -A5 "private frameAxis"
  → Math.min(M, Math.max(v - c - M, want))     （同样是三参数版）
git show HEAD:src/core/renderer.ts | grep padX
  → padX: 72
```

HEAD 版本就已经如此。它是「可读优先取景（`anchorX = vw * 0.3` 对齐根节点）」
配「`frameAxis` 钳制」这个**组合**自带的缺陷，只是之前没在这么窄的文档区里跑过。

### 12.8 顺带一条工具教训

这一轮出现**三次「编辑报成功、内容却没变」**（`LAYOUT_PAD_X` 的插入、`fit()` 调用点、
`ux-v2` 的 `canvasW` 字段），其中一次直接让 `tsc` 报 `Cannot find name 'LAYOUT_PAD_X'`。

复查发现是**读到了还没刷盘的旧内容** —— 重新 `Read` 一次就正常了。

教训：**编辑完立刻 grep / Read 复核**，尤其在紧接着要跑 `tsc` / `build` / 测试的时候。
否则会朝着「代码写错了」的方向白查半天，而实际上代码是对的，
只是构建读到了旧文件 —— 那会白白浪费一轮「改了没反应」的困惑。

### 12.9 同一族问题的第二处：`reclampView()` 的判据

修完 `frameAxis` 之后，把用到 `worldW` 的地方全 grep 了一遍，发现 `reclampView()`
犯的是**同一个认知错误**：

```ts
const cw = this.worldW * this.scale;
if (cw <= vw - M * 2) { this.tx = (vw - cw) / 2; }   // ← 判据用了画布宽
```

这里要分清楚：`tx` 用**画布**宽是**对的**（`tx` 就是画布的平移量，画布居中 = 内容居中）；
但「装不装得下」的**判据**该用**内容**宽 —— 用画布宽会漏掉一段约
`2 × pad × scale` 宽（本项目 79px）的窗口：内容明明装得下，却因为画布多裹了一圈内边距
被判成「装不下」，视图不居中，内容偏在一边、另一侧白白空掉。

修法：`innerW = cw - LAYOUT_PAD_X * this.scale * 2` 参与判据，`tx` 仍用 `cw`。

新增 `tests/kernel/diag-reclamp.mjs`（3 条断言，`npm run ux:reclamp`，
已并入 `ux:all` —— 现 **17 支**）。它把那段窗口**直接构造出来**，不用真去折叠一个分支 ——
判据只看 `worldW × scale`，把 `scale` 解进窗口就行：

```
vw=519 · worldW=421 · scale=1.3856 · cw=583.3 · innerW=383.8 · 阈值=463
旧判据 cw <= 463 ?     false  → 不动，tx 保持 -100（内容占 0~384px，右侧空 135px）
新判据 innerW <= 463 ? true   → 居中，tx = -32.17
```

⚠️ 这条测试还纠正了我写在源码注释里的一句**不准确**的话：原本写的是「左侧被裁 42px」，
实测是「内容占 0~384px、右侧空 135px」—— **没被裁，是偏心**。
在注释里写没实测过的数字，就是在给下一个读代码的人挖坑。

**教训**：修完一处，把同一个量（这里是 `worldW`）的所有用法 `grep` 一遍 ——
**同一个认知错误往往不止一处。**

## 十三 · 测试自己也会烂：一个「坐标落在窗口底边」的陷阱

### 13.1 现象

跑 `ux:settings`（`diag-settings.mjs`）得到 **32 通过 / 3 失败**：

```
✗ ctrlWheelZoom=开：Ctrl+滚轮↑ 放大  scale 100 → 100
✗ wheelPan=开：普通滚轮平移画布  translate(22.5px, 0px) → translate(22.5px, 0px)
✗ 开：悬停折叠珠子浮出预览卡片，文案是「折叠了 N 个子节点…」  []
```

三条全是**鼠标手势失效**，而**点击类断言全过**。

诡异之处：**`ux:all` 里同一支是 35 通过 / 0 失败**（两次串跑都是）。

### 13.2 先排除

| 怀疑 | 结论 |
| --- | --- |
| 刚改的 `cdp.mjs`（stdio 从 `ignore` 改成 `pipe`）？ | **完全还原后仍 32/3** → 不是它 |
| `SHORTCUT_HELP` 的文本改动？ | 纯文本，且 `ux:all` 是在那之后跑的 |
| 端口占用 / 残留 Chrome？ | 无占用，Chrome 进程数 0 |
| 临时 profile 累积？ | 只有 9 个目录，Temp 共 2GB，正常 |

### 13.3 让断言自己说清楚

原来的失败信息只有「scale 100 → 100」—— **看不出是没滚到、还是滚了没反应**。

给 `wheelAt` 加上落点诊断：

```js
const d = await page.eval(`(() => {
    const el = document.elementFromPoint(${c.x}, ${c.y});
    return { hit: el ? String(el.className || el.tagName).slice(0, 44) : 'null',
             x: ${c.x}, y: ${c.y}, innerH: innerHeight, scrollY: Math.round(scrollY) };
})()`);
```

一跑就现形：

```
落点 fn__flex-1 @(1337,948) innerH=955 scrollY=0
```

**y = 948，窗口高 955** —— 坐标距底边只剩 7px；落点是思源的布局容器 `fn__flex-1`，
**根本不是导图**。滚轮当然到不了 `.mm-viewport`。

### 13.4 根因

`canvasCenter` 取的是 `.mm-root` 的**矩形中心**，而且**没有先把它滚进可视区**：

```js
const r = root.getBoundingClientRect();
return { x: Math.round(r.left + r.width / 2), y: Math.round(r.top + r.height / 2) };
```

导图高 700~900px 而窗口只有 955px 高 —— `.mm-root` 的矩形中心很容易落到窗口底边附近，
那里 `elementFromPoint` 返回的是**底层容器**，滚轮事件到不了 `.mm-viewport`。

**同一个坑 `ux-v2.mjs` 早就踩过、也留了注释**（`nodeCenter` 里的 `scrollIntoView`
加那段长注释），只是 `diag-settings.mjs` 的 `canvasCenter` 没把它抄过去。

修法两条：**① 取 `.mm-viewport`（真正接收滚轮的那层）的中心；② 先 `scrollIntoView({ block: 'center' })`。**
修后 **35 通过 / 0 失败**。

### 13.5 为什么串跑能过 —— 它一直在「靠运气绿」

对比两次的视图状态：

```
ux:all 里：  ✓ scale 100 → 112 ｜ translate(234px, 0px) → translate(234px, -240px)
单跑：       ✗ scale 100 → 100 ｜ translate(22.5px, 0px) → translate(22.5px, 0px)
```

**平移量不同（234 vs 22.5）** → 视图状态不同 → `.mm-root` 的屏幕位置不同 →
中心点**恰好**在串跑时落在有效区域、单跑时落到窗口底边。

**所以这三条断言一直在靠运气绿。** 串跑时前面 14 支脚本留下的时序差异，
刚好让坐标躲过了这个坑。**它不是「环境偶发」，是一条一直存在的测试缺陷，只是被遮住了。**

这也解释了为什么「单跑红、串跑绿」这种反常组合值得追：**正常的脆弱性是反过来的。**

### 13.6 顺带：又踩了一次反引号

给 `canvasCenter` 写注释时，在 `page.eval` 的**模板字符串里**写了反引号包起来的
`.mm-viewport` —— 外层模板被提前截断，报 `SyntaxError: missing ) after argument list`。

**这个坑技能里明确写着，我还是踩了。** 唯一可靠的防法：在 `page.eval` 的模板里，
**注释里一个反引号都不要出现**（连行内代码标记也别用）。

## 十四 · 补跑 `check:all` 漏掉的那一半：验收脚本也会静默腐烂

这一轮之前的「质量门」其实只覆盖了 `check` —— 而 `check:all` 还包含 `visual`。
补跑 `npm run visual`，**它直接报错退出**：

```
[mindmap] 可视化验证页已生成 → tests\.build\visual.html
[visual] 页面上没有找到 #report，验证页可能渲染失败
```

### 14.1 现象与第一次误判

`visual-check.mjs` 的判据是：用 `chrome --headless=new --dump-dom
--virtual-time-budget=6000` 抓渲染后的 DOM，正则找 `<pre id="report">`，
找不到就 `console.error` + `process.exit(1)`。

第一反应是「`visual.ts` 被改坏了」—— 但 `git diff tests/visual.ts` **输出为空**，
`visual.mjs` / `visual-check.mjs` 也不在 `git status` 的改动列表里。

于是去数 `dump.html`：

```
mm-root            247
mm-node            104
protyle-wysiwyg      5
id="report"          0      ← 缺的是它
id="app"             1
```

**导图渲染出来了**（247 个 `mm-root`、104 个 `mm-node`），说明脚本跑到了一半。
`report()` 在 `visual.ts` 的模块顶层（第 555 行）调用，任何在它之前的异常都会
让它根本不执行 —— 而 `<pre id="report">` 是**运行时创建**的，模板 HTML 里没有，
所以「页面能看、报告没有」这个组合是自洽的。

### 14.2 手段：`--dump-dom` 会把异常吞掉

`--dump-dom` 只给最终 DOM，不给控制台、不给异常栈。于是写了个诊断脚本
`tests/kernel/diag-visual.mjs`（`npm run ux:visual`），用 CDP 直接加载验证页并订阅：

- `Runtime.exceptionThrown` —— 未捕获异常，带完整栈
- `Runtime.consoleAPICalled` —— 页面里的 console 输出
- `Log.entryAdded` —— 浏览器级日志（含资源加载失败）

一次就现形：

```
=== 未捕获异常 ===
- Uncaught TypeError: this.getFoldOverlay is not a function @ visual.js:2233:27
```

### 14.3 根因一：构造函数第 3 个参数换了类型，验证页没跟上

`MindMapView` 的构造函数第 3 参早已从

```ts
folded: Set<string>
```

改成了

```ts
getFoldOverlay: () => ReadonlyMap<string, boolean>
```

而 `visual.ts` 里传的还是老样子：

```ts
new MindMapView(list, config, new Set<string>(), { /* callbacks */ }, title, mode);
```

`Set` 当然不是函数 → `render()` 里 `this.getFoldOverlay()` 抛 `TypeError`。
**页面渲染到一半就死了**，`report()` 永远轮不到。

### 14.4 真正的根因：验收脚本不在类型检查范围内

改一行就能修好，但「为什么会烂」才是重点。看 `tsconfig.json`：

```json
"include": ["src/**/*.ts"]
```

**`tests/**/*.ts` 根本不在类型检查范围内。** 产品代码改了签名，验收脚本
不会有任何提示 —— 它只会静静地腐烂，直到某天有人真的去跑它。

而这一轮之前，`visual` 一直没被跑到（只跑了 `check`），于是**腐烂了多久都不知道**。

> **两个条件同时成立才会烂这么久：① 不在类型检查范围内；② 不在日常跑的路径上。**
> 缺任何一个，它都会在第一次改签名时就红。修的时候两个都要修。

### 14.5 修法一：补签名，并且不要用空函数糊过去

```ts
// 验证页的写回是同步的，不存在「内核还没更新回来」的空窗，所以覆盖表恒空。
() => new Map<string, boolean>(),
```

### 14.6 顺带挖出第二处：折叠断言 `序列=[true,true]`

修完签名，`#report` 回来了，113 条断言跑起来 —— 只剩 1 条红：

```
✗ 空格切换折叠   序列=[true,true]
```

**这条断言以前从没真正执行过**（页面一崩就 `exit 1`）。

根因是同一个认知的另一面：折叠态的**真相源是大纲自己**，解析器读 `.li[fold="1"]`，
写回链路是 `onFoldChange` → 内核 → DOM 更新。验证页没有内核，
`onFoldChange` 只把回调记进数组、**没落到假 DOM 上**，于是：

1. 按空格 → `n.folded = true` → 记录 `true` → `render()` **重新解析假 DOM** →
   `fold` 属性还是不存在 → `folded` 被读回 `false`；
2. 再按空格 → 又是 `false → true` → 记录 `true`。

**永远只会折叠，永远展不开。**

修法是给验证页补一个「假内核写回」：

```ts
function writeFoldBack(id: string, folded: boolean) {
    const li = document.querySelector<HTMLElement>(`.li[data-node-id="${id}"]`);
    if (!li) return;
    if (folded) li.setAttribute("fold", "1");
    else li.removeAttribute("fold");
}
```

**⚠️ 这里有个更省事但更糟的修法要明确否掉**：把折叠态记进 `getFoldOverlay()`
返回的覆盖表，`render()` 就会一直按它渲染，断言也能绿。

但覆盖表在生产侧是**临时**的 —— 内核把 DOM 更新回来之后它就被清掉了。
在验证页里它会永远留在表上，等于**凭空多出第二个折叠真相源**。
以后真出现「覆盖表没被清掉」的 bug，这里反而验不出来。
**测试为了变绿而绕开产品的真实机制，就是在制造下一个盲区。**

### 14.7 结构性修法：加一道能让它「能红」的门

新建 `tsconfig.tests.json`（`extends` 主配置，`include` 加上 `tests/**/*.ts`，
`lib` 提到 ES2022 以支持 `.at()`），并接进质量门：

```json
"typecheck:tests": "tsc -p tsconfig.tests.json --noEmit",
"check": "… && tsc --noEmit && npm run typecheck:tests && node tests/run.mjs && …"
```

**第一次跑就报 9 个错 —— 全是同一类的静默腐烂：**

```
tests/visual.ts(181,9): error TS2345: … is missing the following properties
    from type 'ViewCallbacks': onEditInSource, onBatchAction, onViewPrefs,
    onOpenBlock, onMarkChange
tests/entry.ts(802,48): error TS2554: Expected 2 arguments, but got 3.
tests/entry.ts(803,54): error TS2554: Expected 2 arguments, but got 3.
tests/entry.ts(815,85): error TS2554: Expected 2 arguments, but got 3.
```

两类：

1. **`visual.ts` 缺了 5 个回调**（`onEditInSource` / `onBatchAction` / `onViewPrefs` /
   `onOpenBlock` / `onMarkChange`）—— 验证页压根没接这些路径。
   补的时候**记进 `Recorder`**，而不是写成 `() => {}`：
   **空函数等于把这条路径重新藏回暗处。**
2. **`entry.ts` 的 `ok()` 少一个参数，9 处调用的第三参被静默丢掉。**
   这正好撞上「断言消息要自带诊断」那条教训 ——
   红的时候只看到「对象参数走 JSON」，看不到真实内容，还得回去改代码才能查。
   签名补成 `ok(cond, msg, detail?)`，失败时拼进消息。

`process.exitCode` 是唯一的 Node 全局，而项目 `dependencies` 是空的、
刻意不引 `@types/node` —— 于是加了一个 `tests/node-globals.d.ts` 只声明用到的字段。
顺带的好处：以后要用新的 Node 能力，类型检查会先拦一下，得先表态。

| 门 | 结果 |
| --- | --- |
| `npm run typecheck:tests` | 9 错 → **0 错** |
| `npm test`（单测） | **298 项全过** |
| `npm run visual` | `#report` 缺失 → **113/113 全过** |
| `npm run check` | 干净（tsc + 测试 tsc + 298 + 打包 119.5 KB + 冒烟 96） |
| `npm run ux:all` | 17 支全绿 |

### 14.9 教训

1. **「跑过质量门」要说清楚跑的是哪一半。** `check:all = check + visual`，
   只跑 `check` 就等于 `visual` 从来没验过。**没跑过的门等于没有门。**
2. **`--dump-dom` 只给结果、不给原因。** 页面「渲染了一半」这种状态，
   它只能告诉你「缺个元素」；要原因必须用 CDP 抓 `Runtime.exceptionThrown`。
   **诊断脚本值得写 —— 它把「猜」换成「读」。**
3. **验收脚本必须有类型检查。** 否则产品改签名它不会红，只会烂。
   这和「测试为了变绿而绕开真实机制」是同一枚硬币的两面：
   **测试也是代码，也要被检查，也不能走捷径。**
4. **断言里的第三个参数被丢掉，是「假绿」的一种。** 断言没红的时候看不出来，
   红了才发现消息里没数字。**类型检查能拦住它 —— 又一个「加门」的理由。**

## 十五 · `ux:all` 里有一半脚本「有判定、没门」

第十四节查的是「验收脚本会不会腐烂」，这一节查的是同一件事的另一面：
**判定算出来了，有没有传出去？**

`ux:all` 是用 `&&` 串起来的 17 支脚本。**脚本只要 exit 0，链子就继续往下走** ——
所以一支脚本即使打印了一屏 `✗`，只要它没设退出码，整条链照样「全绿」。

### 15.1 核查：17 支里 6 支的失败传不出去

```bash
for f in $(ux:all 里的 17 支); do
  grep -q "process.exit(.*fail\|process.exit(1\|process.exitCode = 1" "$f" && echo 有 || echo 无
done
```

结果：

| 脚本 | 有断言/判定 | 失败能传出去 |
| --- | --- | --- |
| `diag-edit-flow` | **13 条 `check()`** | ❌ 只打印 `11/11 项通过` |
| `diag-feedback` | 算出「列数来回跳 = 反馈回路实锤」 | ❌ 只 `console.log` |
| `diag-migrate-layout` | 算出「两种路径一致 ✓ / 不一致 ✗」 | ❌ 只 `console.log` |
| `diag-zoom-measure` | 算出「量测一致 / 不一致」 | ❌ 只 `console.log` |
| `diag-reopen` | 算出「布局确定性 ✓/✗」「单击就退出编辑态 ✗」 | ❌ 只 `console.log` |
| `diag-user-doc` | 算出「重叠/脱节 ✗」「三种打开方式不一致 ✗」 | ❌ 只 `console.log` |

**六支里有四支的判定是「产品坏了」**，却全都能在 `ux:all` 里绿着过去。

### 15.2 修法：`process.exitCode`，不是 `process.exit()`

```js
// ✅ 让 finally 跑完，再让进程以非零码退出
let failed = false;
// ... 每个 ✗ 分支里：failed = true;
} finally {
    await chrome.close();
    await removeDoc(api, docId);   // 临时文档清理
    if (failed) process.exitCode = 1;
}

// ❌ 别这么写：process.exit() 会**跳过 finally**，
//    chrome.close() 与 removeDoc() 都不执行 —— 临时文档就留在用户工作空间里了。
```

### 15.3 ★★ 反转：给 `diag-zoom-measure` 加门，它立刻红了 —— 但它红错了

补上退出码后重跑，**它当场红**：

```
zoom=1        : 157x49 254x40 253x37 …
zoom=0.55     : 159x51 256x42 254x38 …
zoom=1 与 zoom=0.55 量测一致? 不一致 → zoom 影响量测，布局会依赖渲染次序
EXIT=1
```

第一反应是「挖到第 9 个 bug 了」。**但去读产品代码，结论正好相反：**

```ts
// src/core/renderer.ts（这段早就写好了）
// ⚠️ 但必须先把 world 上的 `zoom` 归 1 —— 这是实打实测出来的坑：
// Chromium 下 `offsetWidth` / `offsetHeight` **会被祖先的 zoom 影响**，
// 而且不是等比缩放，是「按 zoom 折算成物理像素 → 四舍五入 → 再折回来」。
// 于是 `zoom: 0.55` 时一个真实 165×57 的节点会量成 167×59（最多多出 1/zoom ≈ 1.8px）。
const prevZoom = this.worldEl.style.zoom;
if (prevZoom && prevZoom !== "1") this.worldEl.style.zoom = "1";
for (const n of all) { n.w = n.el!.offsetWidth; n.h = n.el!.offsetHeight; }
if (prevZoom && prevZoom !== "1") this.worldEl.style.zoom = prevZoom;
```

**实测的 `157x49` vs `159x51` 正好就是注释里写的「最多多出 1/zoom ≈ 1.8px」。**

也就是说：这一支的「不一致」**是它要回答的那个事实本身**，
是 `render()` 里那段「量测前先把 zoom 归 1」的修复**存在的证据**，不是缺陷。
它是一支**回答历史问题的探针**，不是回归断言。

**加门之前必须过一遍这个判据：**

> **这段代码红了，说明「产品坏了」，还是说明「我搞错了」？**
> 前者才配当门，后者只配当诊断。

把「记录一个事实」当成「断言一个期望」，就会造出一扇**永远红**的门 ——
而永远红的门很快就会被所有人无视，比没有门更糟。**已撤回该改动，并在脚本里写明原因。**

### 15.4 顺带：为什么 `grep "✗"` 没发现它

补门之前我先扫了一遍 `ux:all` 的日志，`grep -c "✗"` 返回 **0**，于是判断「全绿」。

**但 `diag-zoom-measure` 的红根本不带 `✗` 字符** —— 它打印的是
「不一致 → zoom 影响量测」。同理 `diag-feedback` 打印的是「画布尺寸也在变」。
**「日志里没有 ✗」不等于「没有红」。** 这也是为什么必须查退出码，
而不是靠肉眼看日志里的符号。

### 15.5 修完的账

| 脚本 | 处理 |
| --- | --- |
| `diag-edit-flow` | 补 `process.exitCode`（13 条断言终于能传出去） |
| `diag-feedback` | 补（列数稳定是期望，红了说明反馈回路回来了） |
| `diag-migrate-layout` | 补（两条路径一致是期望） |

### 15.7 教训

1. **「脚本跑完了」和「脚本验过了」是两件事。** `&&` 串联只保证「没崩」，

2. **补门之前先问：红了说明产品坏了，还是我搞错了？** 只有前者才配当门。
   **永远红的门比没有门更糟 —— 它会被无视。**
3. **不要用日志里的符号判断红绿。** 去查退出码。
4. **`process.exitCode` 而不是 `process.exit()`** —— 后者会跳过 `finally` 里的清理，
   测试自己留垃圾和功能有 bug 一样糟。

### 16.4 结构性修法：`npm run lint:tests`

这轮的坑有两个共同点：**① 都在从未跑过的脚本里；② 都是「几毫秒就能查出来」的东西。**

所以加了 `scripts/lint-tests.mjs`，只做两件事：

| 检查 | 拦什么 |
| --- | --- |
| `node --check` 解析每个 `.mjs` | 拦「`page.eval` 模板字符串里写反引号」把外层模板截断 |
| 解析每个相对 `from "…"` / `import("…")` 是否存在 | 拦 `./cdp.mjs` 这类写错的路径 |

```json
"lint:tests": "node scripts/lint-tests.mjs",
"check": "… && npm run typecheck:tests && npm run lint:tests && node tests/run.mjs && …"
```

**「能红」对照**（造一个 canary 文件，跑完删掉）：

```
坏 import          → ✗ tests/kernel/__lint-canary.mjs  [import]  ./cdp.mjs      EXIT=1
反引号陷阱         → ✗ tests/kernel/__lint-canary.mjs  [语法]  …:2              EXIT=1
删掉 canary 后      → ✓ 语法与相对 import 全部通过                              EXIT=0
```

⚠️ 写这个脚本本身也踩了一个坑：**它自己的文档注释里写了 `from "./x"` 这种示例**，
于是第一次跑，它把自己报成 4 处坏 import。所以扫之前要先剥掉块注释与整行注释 ——
但**不能**粗暴按 `//` 截断，因为代码里有 `"http://127.0.0.1:6806"` 这种字符串。

> `node --check` 只解析、不执行，所以「跑起来才知道」的错误它拦不住。
> 它的定位是**语法级的最低防线**，不替代真跑。

### 16.5 关于反引号：这是本轮第三次踩

`page.eval` 的模板字符串里，注释中的反引号会把外层模板提前截断，
报 `SyntaxError: missing ) after argument list`，**而报错行号指向模板开头**，
和真正的问题（某行注释里的反引号）差着几十行。

**技能里明确写着这条，本轮仍然踩了三次。** 所以这次的结论不是「下次注意」，而是：

> **靠自觉不行的事，就别靠自觉。** `node --check` 几毫秒就能查出来 —— 加进 `check`。

4. **判据要复用。** 第十五节立的「红了说明产品坏了还是我搞错了」，

## 十七、第 9 个真 bug：退出编辑态不归还焦点 → 导图键盘整体失效

### 17.1 现象

`npm run live`（本轮第一次跑）给出 **23/26**，三条红全部指向同一个动作：

```
✘ Ctrl+Z 能撤销「加子节点」   — 加子节点：7 → 8 → Ctrl+Z 后 8
✘ 撤销后焦点仍在导图上        — mm-txt
✘ 重做之后还能再撤销
```

同时「删除节点 → Ctrl+Z」那条是**绿的**。差别在哪？删除前刚点过节点、焦点还在导图上；
而「加子节点」用的是 `Tab` —— 它会把新节点**带进编辑态**。

### 17.2 第一假设，以及它被证伪

读码得到的假设很顺：编辑态的 `onKey` 是无条件 `e.stopPropagation()` 的，
只认 Enter / Esc，Ctrl+Z 被它吃掉 —— 既没被插件的历史栈接住、也没冒泡给思源。

于是写了 `tests/kernel/diag-undo-after-insert.mjs`，**三组对照**：

| 组 | 动作 | 期望 |
| --- | --- | --- |
| A | Tab 后直接 Ctrl+Z | 内核不变（复现） |
| B | 先 Esc 再 Ctrl+Z | 内核回到 Tab 之前 → 说明是编辑态挡的 |
| C | 不在编辑态时插入再撤销 | 能撤销 → 说明历史栈本身是好的 |

实测（修复前）：

```
════ A. Tab 之后直接 Ctrl+Z
  Tab 后: ["0:根节点","1:甲","2:新节点","1:乙"] 焦点: mm-txt
  Ctrl+Z 后: 同上                                焦点: mm-txt
  → ✘ 没撤销掉（内核仍多一项）
════ B. 在同一状态上先 Esc 再 Ctrl+Z
  Esc 后: … 焦点: fn__flex-column body--windows body--win32-browser   ← 焦点已经不在导图上了
  Ctrl+Z 后: 同上
  → ✘ 仍未回到操作前
════ C. 对照
  → ✘ 仍未撤销 —— 问题不在编辑态
```

**B、C 组也失败了 → 假设被证伪。** 但失败里冒出了真线索：Esc 之后焦点跑到了
`fn__flex-column` —— 那是思源的**布局容器**，早就离开了导图。

> 对照实验的价值在于它能**证伪**，不只在于它能证实。
> 如果只做 A 组，我会拿着一个错的假设去改 `onKey`，然后发现改不动。

### 17.3 真根因

`renderer.ts` 的 `finish()`（退出编辑态）做了四件事：置 `editing = null`、
去掉 `contenteditable`、提交改名、补做 `pendingRender` —— 唯独**不归还焦点**。

焦点因此落在布局容器上。而导图的键盘是「全局分发器 + `rootEl.contains(e.target)` 才处理」
（见 `handleGlobalKey`），焦点一离开导图，**整套键盘一起失效**：
方向键 / Tab / Enter / 空格 / Ctrl+Z 全都不响应。

其中 Ctrl+Z 最刺眼：按下去**完全没反应** —— 既没被插件接住，也没冒泡给思源，
用户会以为「撤销坏了」。

### 17.4 修法：只在「键盘主动退出」时归还

```ts
const finish = (commit: boolean, refocus = false) => {
    // …原有四件事…
    if (refocus) this.restoreFocus();
};
// onKey 里：
if (e.key === "Enter")  { e.preventDefault(); finish(true,  true); }
else if (e.key === "Escape") { e.preventDefault(); finish(false, true); }
// onBlur 里的 finish(true) 保持不变
```

**关键是不能无脑归还**：点别处导致的 blur 也会走 `finish`，
那时去抢焦点会把用户从他**刚点进去的地方**拽回来（刚点进思源编辑器、刚打开命令面板……）。
这与 `restoreFocus()` 里「只抢被思源编辑器抢走的那种焦点」是同一条纪律。

修复后同一支探针：

```
════ B. 先 Esc 再 Ctrl+Z
  Esc 后: … 焦点: mm-root          ← 从 fn__flex-column 变回 mm-root
  Ctrl+Z 后: ["0:根节点","1:甲","1:乙"]
  → ✔ 撤销成功
════ C. → ✔ 撤销成功（插件历史栈本身是好的）
```

### 17.5 A 组仍然是红的 —— 但那是设计，不是缺陷

修复后 A 组照旧 ✘。这时要用第十五节立的判据问一句：

> 这段代码红了，说明**产品坏了**还是**我搞错了**？

答案是「我搞错了」。`onKeyDown` 的**首行**就是 `if (this.editing) return;` ——
编辑态下键盘**整体让位给输入框**，这是刻意的：用户在改名字的时候按 Ctrl+Z，
期待的当然是撤销刚敲进去的字（浏览器原生 undo），而不是撤销整个块操作。

所以 A 组不是缺陷，是**用户操作序列不完整**。

### 17.6 断言陈旧：`live.mjs` 少了一次 Esc

那三条断言写在「**Tab 插入即编辑**」这个功能之前 —— 当时 Tab 只插入、不进编辑态，
焦点本来就留在导图上，Ctrl+Z 自然能撤销。功能一改，断言就悄悄失效了。

修法是把动作序列对齐到用户真实会做的那一套：

```js
await page.press("Tab");      // 插入并进入编辑态
await sleep(1500);
const undoAdd1 = await itemShape(doc.listId);
await page.press("Escape");   // ← 补这一次：退出编辑态，焦点还给导图
await sleep(600);
await page.press("z", { ctrl: true });
```

用 `Esc` 而不是 `Enter`：Esc 是「放弃改名」，不会多写一条 rename 记录，
Ctrl+Z 撤掉的正好是插入那一步 —— 这才是本条要测的东西。

「撤销后焦点仍在导图上」的判据也一并写清楚了：用 `/mm-root/` 而不是「焦点在导图内」，
因为 `.mm-txt`（编辑态）**也在导图内**，但那时 Ctrl+Z 没人接。

### 17.7 修完的账

| 项 | 修前 | 修后 |
| --- | --- | --- |
| `npm run live` | 23/26（三条撤销红） | ✅ **26/26** |
| `npm run live:gpu` | 本轮首次跑 | ✅ 通过（GPU 渲染器确认 RTX 4060 Ti） |
| `npm run check` | — | ✅ 298 单测 + 96 冒烟 + lint + 两套 tsc |
| 编辑态退出后焦点 | 掉到 `fn__flex-column` | ✅ 键盘主动退出时回到 `mm-root` |

### 17.8 教训

1. **「退出一个状态」时要问一句：我把用户交还到哪里了？**
   编辑态是「借」来的焦点，退出时**必须还**。这和 `restoreFocus()` 是一体两面 ——
   一边防别人抢，一边防自己弄丢。
2. **但「还」要有条件。** 失焦提交时还焦点，等于把用户从新落点拽回来。
   `finish(commit, refocus)` 的第二参就是这个条件的具象化：
   **只有「用户自己按键盘要走」才还。**
3. **键盘整体失效这类 bug，症状会伪装成别的问题。** 用户看到的是「Ctrl+Z 坏了」，
   根因却是「焦点不在了」。所以诊断时要问「这个键**到底有没有被接到**」，
   而不只是「这个功能有没有生效」—— `diag-undo-after-insert` 里记录焦点正是为此。
4. **功能演进会让旧断言悄悄失效。** 「Tab 插入即编辑」是新功能，
   它把 Tab 之后的焦点状态改了，而三条老断言的前提正是那个旧状态。
   **改交互时，回头扫一遍依赖旧交互的断言。**
5. **判据第三次复用。** 第十五节立的「红了说明产品坏了还是我搞错了」，
   这一节又用了一次（A 组）—— 这次结论是「我搞错了」，所以改测试而不是改产品。

## 十八、探针的「崩溃路径」没有清理，以及那 10 支「无家可归」的脚本

### 18.1 怎么发现的

修完第 9 个真 bug 之后，跑一次 `npm run clean:tmp` 干跑，它报：

```
「临时-」开头的文档 2 个，其中命中签名 2 个
按探针分组：
  行内覆盖度  ×1
  焦点探针    ×1
```

**这两个正是本轮修 bug 时崩掉的那两次留下的** —— `inline-coverage` 崩在
`getBlockDOM({id: undefined})`、`focus-timeline` 崩在坏 import / 属性名。
而它们各自都**写了清理代码**，位置在 `try` 块的**末尾**：

```js
try {
    …主逻辑…
    if (!process.env.MM_KEEP) {
        const info = (await api("/api/block/getBlockInfo", { id: docId })).data;
        await api("/api/filetree/removeDoc", { notebook: info.box, path: info.path });
        console.log("已清理临时文档");
    }
} finally {
    await chrome.close();     // ← finally 里只有关浏览器
}
```

**异常一抛，控制流直接跳到 `finally`，清理那几行永远执行不到。**
所以「崩溃 → 漏文档」是必然的，不是偶发。

### 18.2 全仓扫一遍：三种形态

拿「清理写在哪」当判据扫 75 个文件，结论是三种：

| 形态 | 支数 | 风险 |
| --- | --- | --- |
| 清理在 `finally` 里（正常） | 33 | ✅ |
| **清理在 `try` 末尾** | **4** | ⚠️ 一崩就漏（`focus-timeline` / `image-probe` / `inline-coverage` / `measure-scale`） |
| **顶层 await，没有 `try/finally`** | **4** | ⚠️ 崩了连浏览器都不关（`copy-fidelity` / `insert-shapes` / `restore-roundtrip` / `live-gpu`） |

顺带查出两个「清理 API 不统一」的问题：

- 同一件事有三种写法：`getBlockInfo` 取 `info.data.box`、取 `info.box`、
  以及 `_doc-cleanup.mjs` 里验证过的两步法（`getPathByID` → `removeDoc`）。
  **`live.mjs` 里甚至有一份自己的本地实现** —— 取的是**顶层** `info.box`，
  而别的脚本取 `info.data.box`。两种写法并存本身就说明这个字段路径不牢靠。
- 好几处的失败被 `catch` 吞成一句 `console.warn`，**不传退出码**。

### 18.3 修法

**高风险的 4 支（清理在 `try` 末尾）** —— 把清理挪进 `finally`，并统一走助手：

```js
} finally {
    await chrome.close();
    /* ⚠️ 清理必须在 finally 里，不能在 try 末尾 —— 本支就崩过两次，
       一崩就跳过清理，在用户笔记本里留下「临时-行内覆盖度-时间戳」。 */
    if (docId && !process.env.MM_KEEP) {
        const ok = await removeDoc(api, docId);
        console.log(ok ? "已清理临时文档" : "⚠️ 临时文档未能清理: " + docId);
    }
}
```

`measure-scale.mjs` 结构特殊（**每轮循环建一份文档**，`docId` 是循环内的 `const`，
`finally` 里够不着）—— 在外层留一个「当轮还没删掉的那个」的引用，正常路径删掉后置空，
`finally` 里只对非空的做兜底。

**探针性质的两支（`copy-fidelity` / `restore-roundtrip`）** —— 没做整段缩进改造，
理由写在注释里：探针跑得少、收益低于改动风险。但**清理 API 统一 + 失败出声**这两点必须做到，
并且明确写下「万一真漏了，用 `npm run clean:tmp` 扫掉」。

**`live.mjs`** —— 删掉本地那份 `removeDoc`，改用助手；`finally` 里改成
「成功/失败都打印」。

### 18.4 顺手给它们一个「家」：`npm run e2e:all`

第十六节 16.7 第一条写的是：

> **「不在任何套件里的脚本」= 必然腐烂的脚本。要么把它接进套件，要么接受它会烂。**

当时只是记下这句话，这一轮把它落地了。新增：

```json
"e2e:all": "npm run kernel:shapes && npm run kernel:restore && npm run kernel:focus
            && npm run kernel:inline:all && npm run kernel:image && npm run kernel:copy
            && npm run ux:tour && npm run ux:scale && npm run live && npm run live:gpu"
```

**为什么单开一支而不是塞进 `ux:all`**：这 10 支都要求思源在跑、单支 30~60 秒，
全串起来约 10 分钟。塞进 `ux:all` 会把它从 12 分钟推到 20+ 分钟，
让「快速回归」这件事本身变得没人愿意做。**门的意义取决于有人愿意按它。**

### 18.5 顺带：补上「有判定、没门」的最后一块

修完清理之后，顺手把这次扫出来的另一件事做掉了 —— `inline-coverage.mjs` 有**三处真断言**
却只打印 ✔/✘、不返回退出码：

- 改名后原有格式是否保住（`格式丢了`）
- `Ctrl+D` 是否插出新块
- `Ctrl+单击` 是否打开链接

这三条都是「产品应该做到的事」，红了就说明产品坏了 —— **配当门**。
加了 `problems` 收集器 + 末尾 `process.exitCode = 1`。

⚠️ 但同目录的 `copy-fidelity.mjs` **不加** —— 它也打印一堆 ✘，
可那是**探针结论**（「这种格式复制后会丢」正是它要记录的事实）。
给它加门会造出一扇永远红的门。**同一条判据（第十五节）第四次派上用场。**

### 18.6 教训

1. **「有清理代码」≠「清理会执行」。** 判据要问：**异常路径上它会执行吗？**
   写在 `try` 末尾的清理，等于只覆盖了「一切顺利」这一条路径。
2. **资源释放要放在 `finally`** —— 这不只是「好习惯」，本项目里它的代价是
   **往用户笔记本里漏文档**（历史上积到 143 个才发现）。
3. **同一件事的 N 种写法，N 越大越说明没人管。** 清理这一个动作有 3 种写法、
   其中一种只在 `live.mjs` 里存在 —— 这种「孤本」正是最该合并的信号。
4. **失败要出声。** 清理失败被 `catch` 吞成 `warn`，就等于「漏了也没人知道」。
   要么传退出码，要么至少把文档 ID 打出来。
5. **门要有人愿意按。** 新套件单开一支、不拖慢已有的，是让「门」活下来的前提。

## 十九、探针全绿，以及「探针不会红，只会给出过时的结论」

### 19.1 起因

第十八节收尾后，还剩最后一批「从没在任何套件里、也从没被跑过」的脚本：
`probe:*` 共 **14 支**。按第十六节那条「不在任何套件里的脚本 = 必然腐烂」，
它们该有同样的问题。

### 19.2 实测：14/14 全绿

逐个实跑（共约 10 分钟）：

```
probe:unfold / fold / menu / canvas / click / sql / ial / settings
probe:keys / altmod / migrate / settingsfx / flip / settingspersist
    → 全部 EXIT=0，零错误特征
```

侦察时也确认了它们的形态是规范的：**12/14 用了清理助手**，
剩下 2 支（`probe-settings-dom` / `probe-settings-persist`）是**只读探针**、根本不建文档，
所以不需要清理。**没有一支需要 argv**（不依赖「工作空间里恰好存在某个文档」）。

### 19.3 那条判据要修正 —— 它不是普适规律

第十六节写的是「不在任何套件里的脚本 = 必然腐烂」。`probe:*` 这批**推翻了这个绝对化表述**：

| 批次 | 是否在套件里 | 实跑结果 |
| --- | --- | --- |
| `kernel:*` / `live` / `ux:tour` / `ux:scale` | ❌ | ⚠️ 烂了（坏 import + 5 处属性读错 + 无门） |
| `probe:*` | ❌ | ✅ 全绿 |

差别在哪？**前者是「回归断言」，后者是「一次性探针」。**

- 回归断言的前提是「**产品行为应当长期不变**」—— 产品一改，前提失效，而断言不会自己报警；
- 探针的前提是「**回答一个具体问题**」—— 问题回答完，它的使命就结束了。

所以正确的表述是：

> **「有判定、且该长期有效」的脚本不接套件 = 必然腐烂。**
> 一次性探针不在其列 —— 但也**不该指望它来守什么**。

### 19.4 但探针有它自己的病：不会红，只会给过时结论

这一轮恰好撞见一个实例。扫「`Tab` 之后紧跟断言」的用法时发现
`diag-canvas-v2.mjs` 有**两处收尾**：

```js
await page.press("Escape");     // 退出编辑态
await page.press("Delete");     // 删掉刚插入的节点
await sleep(900);
// ← 没有任何断言
```

在修 `finish()` 之前，`Escape` 之后焦点掉到布局容器，**`Delete` 根本没人接** ——
也就是这两处收尾**一直没生效**。但后面的断言各自取基线，于是「收尾没删掉」这件事
**从头到尾没人知道**。

它不是「红了没人看」，而是**压根不会红**。这正是探针类代码最危险的地方：

> **断言错了会红；探针错了会安静地给出一个错结论。**
> 所以对探针的要求不是「接进套件」，而是「**只做不验的地方，要单独审一遍**」。

已给这两处补上收尾断言（`total` 回到起点 / 比 Tab 之后少 1）。

### 19.5 教训

1. **判据要能修正。** 「不接套件必然腐烂」在 `probe:*` 上不成立 ——
   区别不在「在不在套件里」，而在「**它是不是一个该长期有效的断言**」。
2. **探针不会红，只会给过时结论。** 这是它比断言更隐蔽的地方：
   断言失效至少会有人看见红，探针失效是静默的。
3. **「只做不验」的步骤要单独审。** 收尾、清理、重置这类「动作」最容易只写不做验证 ——
   而它们往往**隐性依赖焦点 / 时序**，一旦环境变了就静默失效。
4. **侦察先行，别急着批量跑。** 先确认「哪些需要 argv、哪些建文档」，
   再决定怎么跑 —— 否则可能造出一批无人清理的垃圾。

## 二十、i18n 现状盘点：声明了 14 个键，实际接上 4 个

### 20.1 盘点结果

`i18n/zh_CN.json` 与 `i18n/en_US.json` 各有 **14 个顶层键**（两边键名一致 ✓）。
逐个查「这个键到底被谁用了」，结果：

### 20.2 这不是「要不要支持英文」，而是「有机制没用」

```
src/ 里含中文的字符串字面量（粗估）
  src/core/renderer.ts    169
  src/index.ts            127
  src/core/scanner.ts      55
  src/utils/api.ts         17
  src/core/theme.ts        13
  …其余各文件              12
  ───────────────────────────
  合计                    ~400 处
```

所以现状是：**i18n 的管道接好了，但水几乎没往里流。**

### 20.3 改造范围评估（这是为什么它该单独拍板）

~400 处不是一个小改动，而且**不是所有中文都该进 i18n**。按「谁看得见」分三层：

| 层 | 例子 | 该不该进 i18n |
| --- | --- | --- |
| **用户可见 · 高频** | 右键菜单项、工具条 tooltip、设置项标题与说明、`showMessage` 提示 | ✅ 该进 |
| **用户可见 · 低频** | 快捷键帮助浮层、诊断信息面板 | ✅ 该进（但可晚一步） |
| **开发者可见** | 控制台 `console.warn`、内核 API 报错回显 | ❌ 不进（进 i18n 只是徒增翻译负担） |

**并且有一个前置的架构问题**：`renderer.ts` 里那 169 处文案要接 i18n，
就得让 renderer 拿到 `i18n` 对象 —— 目前它只通过 `options` / `cb` 拿回调。
这一步会牵动 `renderer.ts` 的构造函数与所有调用点（`scanner.ts` 里有若干处）。
**这是本次评估里唯一有「结构性成本」的地方，也是建议先定范围的原因。**

### 20.4 建议的分步做法

1. **第一步（小、无架构改动）**：把已经声明却没用上的 **10 个键接上**。
   它们分布在菜单 / 导出路径上，收益是「消除声明与实现的不一致」。
2. **第二步（中等）**：把 `options` 传入 renderer，再抽「用户可见·高频」那一层。
3. **第三步（可选）**：快捷键帮助浮层（`SHORTCUT_HELP`，14 行文案）——
   它是单一常量，抽起来最容易，只是内容多、需要英文翻译。
4. **不做**：控制台日志与内核报错回显保持原样。

### 20.5 结论

**这件事需要先定范围再动手**，不适合顺手改：

- 只做第一步 → 约十几处改动，低风险，能消除「声明未用」；
- 做第一 + 二步 → 要动 `renderer.ts` 的构造签名，属于结构性改动，得配套跑 `ux:all` 全量回归；
- 全量 → ~400 处 + 英文翻译，是独立一轮的工作量。

**当前不改**（记录在此备查）。等确定范围后再执行。

## 二十一、i18n 第一步落地：10 个「声明未用」的键接上了

> 范围由用户拍板：「只做第一步」——接上已声明却没用的 10 个键，
> 不抽那 ~400 处散落文案、不改既有中文行为。

### 21.1 注入路径：为什么挂在 `cb` / `ScannerHooks` 上

视图层（`renderer.ts`）拿不到 `i18n` —— 它只有 `options`（用户配置）和 `cb`（回调）。
要让视图里的布局名、导出菜单走词表，就得把词表递进去。两个候选：

| 方案 | 问题 |
| --- | --- |
| 塞进 `options: MMConfig` | ❌ `MMConfig` 是**用户配置**，会写进块属性、跟着文档走；词表是**运行时环境**，生命周期不同，混在一起会污染配置语义 |
| 加进 `ViewCallbacks`（可选字段） | ✅ 三个构造点只需在字面量里补一行；可选 ⇒ 既有调用完全不受影响 |

选了后者，并在 `ScannerHooks` 里同样加一个 `i18n?`（扫描器再透传给每个视图）。
**两处都标成可选**，所以「没传词表」时视图回退到内置中文 —— **行为与改动前逐字一致**。

视图里加了唯一的取值入口：

```ts
private t(key: string, fallback: string): string {
    const v = this.cb.i18n?.[key];
    return typeof v === "string" && v ? v : fallback;
}
```

**回退逻辑只写一次**（将来要做「缺键告警」也只有一处要改）。

### 21.2 接了哪些

| 键 | 落点 |
| --- | --- |
| `pluginName` | 顶栏图标 title |
| `menuRoot` | 块菜单的子菜单根项 |
| `menuOutline` | 块菜单里的「大纲视图（关闭导图）」 |
| `layoutLogic` / `layoutMind` / `layoutTree` | 块菜单的布局切换项 + 视图工具条的分段控件 |
| `exportPng` / `exportSvg` | 视图的导出菜单 |
| `exported` / `exportFailed` | 导出成功的提示 / 导出失败的提示 |

`EDGE_OPTIONS`（曲线 / 直角折线）**没动** —— 词表里本来就没有对应的键，
它不属于「声明未用」的范畴（属于第二步要新增的）。

### 21.3 ★ 怎么验证「真的接上了」—— 这里必须做能红对照

中文环境下 **fallback 与词表值同值**，所以「界面显示中文」这件事
**既可能是 i18n 生效，也可能是压根没接上、走了 fallback** —— 外观完全一样。

所以验证不能看界面，要让**词表值 ≠ fallback**：

1. 临时把 `zh_CN.json` 的 `pluginName` 改成 `大纲导图【i18n探针】`；
2. 部署，用一次性探针读页面里的顶栏 label；
3. 看它有没有跟着变。

实测结果：

```
i18nPluginName: "大纲导图【i18n探针】"
labels: [..., "大纲导图【i18n探针】", ...]   ← 顶栏按钮的 label 跟着变了
```

**变了 ⇒ 词表确实被读到并渲染**（不是 fallback）。验证完立刻改回、重新部署、删掉探针。

> 这条经验可以推广：**当「正确」与「错误」产出相同外观时，验证必须制造差异**。
> 否则你验证的是「界面是中文的」，而不是「i18n 通了」。

### 21.4 已知的不完美（有意留下的）

`已导出选中的 N 个节点` 是**拼接**式（`t("exported")` 当「已导出」前缀）。
中文下与原样逐字一致，但英文下会得到 `Exported选中的 N 个节点` 这种混搭。

**这是有意接受的**：这一步的目标是「把声明未用的键接上、且不改中文行为」，
不是「把这句话做成可翻译模板」。第二步做完整 i18n 时应把它换成占位符模板
（如 `exportedN` = `已导出选中的 {n} 个节点`）。代码里已就地点明。

### 21.5 还没做的（第二步）

- 抽「用户可见·高频」那一层（菜单项 / tooltip / 设置项 / 提示），~400 处里的多数；
- 把拼接式提示改成占位符模板；
- 给 `EDGE_OPTIONS` 等**新增**词表键；
- 英文环境的实测（本步只验证了「取值路径通」，没验证英文翻译质量）。

## 二十二、i18n 第二步：394 处用户可见文案全部接上

第一步把 10 个「声明未用」的键接上了，那只是把管道通开。这一步把水灌满：
**`src/` 里用户可见的中文，一处不剩**（`npm run i18n:audit` 的「待抽」归零）。

### 22.1 为什么这一步不能靠手工

盘点结果：**212 种文案、256 处**（不含常量表）。看着不多，但：

- 同一个词反复出现（`关闭` 8 次、`本图` 3 次、`Ctrl 双击` 3 次…），手工改必然出现
  「同一个词在不同地方落到不同的键」；
- 237 个静态键 + 63 个动态键，手抄进 JSON 一定会漏、会拼错；
- **键名拼错在中文环境下看不出来** —— `t("menu.inserChild", "插入子节点")` 拼错了键，
  fallback 照样把「插入子节点」显示出来，界面一切正常，只有英文用户会看到中文。

所以这一步的做法是**先造工具，再用工具改**，最后让工具守门。

### 22.2 三个脚本，各管一段

| 脚本 | 职责 | 关键设计 |
| --- | --- | --- |
| `scripts/i18n-audit.mjs` | 捞出「字符串字面量里的中文」并分类 | **用 TS AST，不用 grep** |
| `scripts/i18n-apply.mjs` | 按「中文 → 键名」映射表批量替换 | 精确字面量匹配 + 唯一性断言 |
| `scripts/i18n-keys.mjs` | 生成词表 + 四道校验 | 静态键 + 常量表推导 + langKey |

**为什么 audit 必须用 AST**：本项目注释极多，`grep -c '[一-龥]'` 会给出
renderer.ts「1040 行含中文」这种数字 —— 里面绝大多数是注释，完全没有指导意义，
只会让人误以为有上千处待抽。AST 能精确到「字符串字面量」，还能判断它是不是在
`console.warn` / `throw` / `new Error` 里（那三类不该进 i18n）。

**为什么 apply 用映射表**：一张「中文 → 键名」的表保证了同一个词在任何地方都落到
同一个键。替换是精确字面量匹配 + 「恰好命中一次」断言，改不到别处去。

**为什么 keys 要读常量表**：`t(\`act.${kind}\`, ACTION_LABEL[kind])` 这类调用的键名
静态拼不出来，但值全在常量表里。脚本直接读常量表补进词表 —— 常量表加一条，
词表跟着多一条，不会漏。

### 22.3 抽取的策略：什么该进，什么不该

方案（第二十节）里的三层分类在实施时又长出一层：

| 层 | 例子 | 处理 |
| --- | --- | --- |
| 用户可见 | 菜单项、tooltip、`showMessage` 提示、设置项、对话框 | ✅ 全部抽 |
| 开发者可见 | `console.warn`、`throw`、`new Error("SVG 光栅化失败")` | ❌ 不抽（audit 自动识别） |
| **写进文档的内容** | `NEW_NODE_TEXT = "新节点"` | ❌ 不抽 |
| 诊断信息正文 | `===== 大纲导图 诊断信息 =====`、`--- 配置 ---` | ❌ 不抽 |

第三层是这次新想清楚的：`NEW_NODE_TEXT` 是**写进用户笔记的内容**，不是界面文案。
它跟着文档走、会被导出、会被全文搜索 —— 界面语言变了不该改变写进别人笔记里的字。
**笔记用什么语言由用户自己决定，不由界面语言决定。**

第四层的理由不同：诊断信息是**复制出去给开发者排障**的，读者是能看懂中文的维护者，
翻成英文只会让 issue 里的报告中英混杂。界面上的「复制诊断信息」按钮和它的说明照抽，
只有那份「复制出去的报告正文」保持中文。

豁免不用行号白名单（那种东西一改代码就失效），而是在源码里显式标注：

```ts
// i18n-audit-ignore-start
// 理由就写在被豁免的代码旁边
...
// i18n-audit-ignore-end
```

### 22.4 ★ 坑一：`{...Map}` 展开成空对象

`--write` 第一次跑，只写出 3 个键（就是手工列的那 3 个 langKey），
而日志明明打印着「静态 237 · 动态 63」。

根因：`staticKeys` / `dynamicKeys` 是 `Map`，`{ ...aMap }` 展开出来是 `{}` ——
Map 不是普通对象，展开它拿不到任何键值对。要 `Object.fromEntries(map)`。

**教训**：`Map` 和对象字面量长得像、用得像，但在展开 / 序列化 / `JSON.stringify`
这三件事上行为完全不同。日志里「统计数对、结果数不对」是这类 bug 的典型信号。

### 22.5 ★ 坑二：`scanner.ts` 是 CRLF

批量替换脚本按 `\n` 拼多行匹配串，renderer / index / api 都改了，**scanner 的 12 处一处没中**。

查下来：`scanner.ts` 全文 CRLF（1427 行），其余源文件是 LF。

修法：脚本读文件时探测行尾，把匹配串里的 `\n` 换成探测到的行尾再匹配。
（脚本本身保持「任一处不命中就整体不写盘」，所以那 12 处是干净地失败，没有半途改坏。）

**教训**：跨文件批量改代码时，「行尾」是和「编码」「缩进」并列的一维，
必须先探测再匹配。而且——**批量脚本要有原子性**，否则会出现「改了一半」的中间态。

### 22.6 ★★ 坑三：改的是构建产物，不是真源

这是这一步最值得记的一个坑。

`--write` 把 296 个键写进了根目录的 `i18n/zh_CN.json`，`--verify` 报绿
（「zh_CN 296 键 / en_US 296 键，代码静态键 237 个全部命中」）。
**但下一次 `npm run build` 就把它原样覆盖回旧的 14 个键。**

根因：`scripts/build.mjs` 里白纸黑字写着 ——

> ⚠️ 根目录的 `i18n/` 是**构建产物**，真源是 `src/i18n/` —— 这里会先删后建。
> 改文案请改 `src/i18n/*.json`；直接改根目录那份，下一次构建就会被原样覆盖回去，
> 而且因为 index.js / plugin.json 走的是另一条 copyFileSync 路径、每次都正常更新，
> 现象会变成「代码改了生效了、文案改了死活不变」，非常难排查。

而我的校验脚本读的正是**构建产物**。所以它绿得毫无意义 ——
它校验的是「我刚写进去的那份」，不是「真正会被打进包里的那份」。

**这是「门装错了地方」的一个标准样本：比没有门更危险，因为它会给你一个假的安心。**

修法两条：
1. 脚本路径指向真源 `src/i18n/`；
2. 补第四道校验：**根目录产物必须与真源一致**，不一致就报错提示 `npm run build`。

发现它的过程也值得记：改完之后我跑 `wc -l i18n/zh_CN.json` 想确认行数，
输出是 `16` —— 296 个键的 JSON 不可能只有 16 行。**如果那次我没顺手看一眼行数，
这个坑会一直带到「英文用户打开还是中文」的那一刻。**

### 22.7 拼接式 → 占位符模板

`t()` 加了第三个参数：

```ts
private t(key: string, fallback: string, vars?: Record<string, string | number>): string {
    const v = this.cb.i18n?.[key];
    let s = typeof v === "string" && v ? v : fallback;
    if (vars) for (const [k, val] of Object.entries(vars)) s = s.split(`{${k}}`).join(String(val));
    return s;
}
```

第一步有意留下的那处拼接（`已导出` + `选中的 N 个节点`）换成了 `msg.exportedN` =
`已导出选中的 {n} 个节点`。同类的还有 18 处（`删除节点（含 N 个子节点）`、
`已选 N 个`、`还有 N 个…`、`最多 N 个字`…）。

还有一类更微妙的：**把已经翻译过的片段嵌进模板**。

```
批量{act}失败，已还原到操作前     →  "Batch {act} failed; changes were rolled back"
已{act}：{label}                →  "{act}: {label}"
```

`{act}` 的值来自 `act.<kind>`（中文下「降级」、英文下 "Demote"），
`actionLabel()` 负责取。中文下逐字还原成原文，英文下语序也站得住。

**这类「模板 + 已翻译片段」是拼接式与完整模板之间的中间态**：
它不能解决所有语序问题（比如某些语言动词要放句尾），但足以让英文不出现中英混搭，
且改动量远小于给每种 kind 写一整句。对「14 种 kind × 2 处提示」这种组合，
写 28 个完整句子不划算。

### 22.8 键名规范

- **新键用点号分组**：`menu.*` / `tip.*` / `msg.*` / `dlg.*` / `set.*` / `ui.*` /
  `act.*` / `actionFail.*` / `ghost.*` / `batchDone.*` / `theme.*` / `layout.*` /
  `edge.*` / `filter.*` / `search.*` / `export.*` / `mark.*` / `present.*` / `err.*`
- **旧 14 个驼峰键保留不动**（`pluginName` / `menuRoot` / `exportPng` …）。
  其中 4 个（`migrateLegacy` / `toggleMindMap` / `toggleSidePanel` / `copyDiagnostics`）
  与 `plugin.json` 的 `langKey` 耦合，为了「命名统一」去动它们纯属给自己找麻烦。
- **例外**：`layoutLogic` / `layoutMind` / `layoutTree` 三个改成了 `layout.logic` 等 ——
  因为它们有 3 个同族兄弟（`edge.*` / `theme.*` / `filter.*` 全是点号），
  留 3 个驼峰会让词表里同一类东西两种风格。
- `exported` 键删除（被 `msg.exportedN` 取代）。

### 22.9 四道校验，各抓什么

接进 `npm run check`（`npm run i18n:check`）：

| # | 校验 | 抓什么 |
| --- | --- | --- |
| ① | 代码里的静态键 ⊆ 词表 | **键名拼错** —— 中文环境下 fallback 会把它掩盖 |
| ② | zh_CN 与 en_US 键集合一致 | 加了中文忘了英文（或反之） |
| ③ | en_US 里不残留中文 | 英文没翻，直接抄了中文 |
| ④ | 根目录产物与 `src/i18n/` 一致 | 改了真源忘了 build（22.6 那个坑） |

①是关键：**它是唯一能抓住「拼错键名」的手段**。没有它，这类错误会一直潜伏到
第一个英文用户出现。

补上「全页面扫 `title` / `aria-label`」之后才 6/6。

> **「实现一样所以不用分别验证」是个危险的假设。** 两条注入路径的代码确实几乎相同，
> 但它们由不同的对象持有、在不同的时机被赋值 —— 其中一条没接上，另一条照样是绿的。

验完立刻改回词表、重新构建部署，并核对部署件里无探针残留（`0 个残留`）。

### 22.11 教训

1. **改文案之前先问「哪一份是真的」。** 有构建步骤的项目里，源目录和产物目录
   常常长得一模一样。写之前花十秒确认，能省掉一整轮的返工。
2. **校验必须盯真源。** 门装错地方比没有门更危险 —— 它给的是假的安心。
3. **「能红对照」要推广到 i18n 的每一层。** 中文环境下词表值与 fallback 同值，
   「界面显示中文」既可能是 i18n 生效、也可能只是 fallback。验证必须让词表值 ≠ fallback。
4. **`Map` 不是对象。** `{...map}` 是空的。日志里「统计数对、结果数不对」要立刻想到这条。
5. **批量改代码时，行尾和编码是一等公民。** 而且脚本必须有原子性。
6. **不是所有中文都该进 i18n。** 「写进用户文档的内容」和「给开发者看的报告」
   都不该翻 —— 前者的语言由用户决定，后者翻了反而更难读。

## 二十三、i18n 第三步：快捷键速查，以及顺出来的两个「门的问题」

第二步收口时剩下最后一块没接 i18n 的界面文案：设置面板里的**快捷键速查**（`SHORTCUT_HELP`）。
它被方案第二十节列为「第三步（可选）」—— 理由是「它是单一常量，抽起来最容易，只是内容多、
需要英文翻译」。真做起来发现，最容易的那一块反而暴露了两个更值得写下来的问题。

### 23.1 起点

```
src/index.ts:25   const SHORTCUT_HELP = [ "导航：…", "编辑：…", …, "⌥⌘D …" ].join("\n");
src/index.ts:895  btn.onclick = () => showMessage(SHORTCUT_HELP, 12000);
```

14 行文案（含 1 个空行分隔）、模块级常量、一个消费点。因为是模块级常量，
**不能用 `this.t()`** —— 取值只能在类内做。

### 23.2 下标键 vs 语义键：这里选了后者

最省事的做法是按下标取：`this.t(\`shortcut.${i}\`, SHORTCUT_HELP[i])`。
它有个不报错的失败模式：**中间插一行，后面所有译文整体错位**。

错位之后，界面依旧是一句通顺的英文 —— 不是乱码、不是 `undefined`、不报任何错，
只是「编辑」那一行显示的是「剪贴」的内容。中英文环境下都看不出来，因为
中文走的是 fallback（按位置对齐，永远正确），只有英文用户会看到内容错行。

所以改成**键名写在数据里**：

```ts
/**
 * 每行配一个**语义键**，而不是 `shortcut.0`…`shortcut.13` 这样的下标键 ——
 * 下标键在中间插一行时，后面所有译文会整体错位，而且错得很安静。
 *
 * 第一项是键名，第二项是内置中文（词表取不到时的兜底）。
 * 空行用 `["", ""]` 占位 —— 它分隔「图内」与「全局」两组，本身没有文案。
 */
const SHORTCUT_HELP: Array<[string, string]> = [
    ["shortcut.nav", "导航：↑↓ 同级 · ← 父节点 · → 第一个子节点 · Home/End 首尾 · 空格 折叠"],
    …
    ["", ""],
    ["shortcut.globalTitle", "全局（在文档任意位置都生效，可在「设置 → 快捷键」里改）："],
    ["shortcut.global", "⌥⌘D 把光标所在的列表切换为导图 / 大纲 · ⌥⌘V 并排面板打开导图"],
];
```

消费点收成一个方法：

```ts
private shortcutHelp(): string {
    return SHORTCUT_HELP.map(([key, zh]) => (zh ? this.t(key, zh) : "")).join("\n");
}
```

`inModuleLiteral` 会沿父链走到外层数组字面量，所以这 14 行仍归 `const` 类
（中文留作 fallback），不需要豁免标记 —— 审计脚本不用改。

### 23.3 ★ 顺出来的缺口一：动态键从来没被校验过

给提取脚本加「键写在数据里」这种形式时（`readKeyedPairs`），才发现一个更早的问题：

`--verify` 的四道校验里，**① 只查了静态键**（`t("字面量", …)`）。动态键 ——
那 63 个由常量表推导出来的 —— **一道校验都没覆盖**。它们只是被 `--write` 写进去，
但没有任何东西在事后检查「写进去了没有」。

这个缺口在这一步刚好会咬人：`this.t(key, zh)` 传的是**标识符**，不是字符串字面量，
所以静态键那条路**根本照不到它**。如果忘了重跑 `--write`，现象是：

- `i18n:audit` 绿（没有「待抽」）
- `i18n:keys --verify` 绿（静态键全命中）
- 界面：英文用户看到 14 行中文，不报任何错

补上 ①'：

```js
// ①' 由常量表推导的动态键同理 —— 少查这一道，常量表里加了条目却忘了重跑
//     `--write` 时，界面会静默退回中文兜底，中文环境下完全看不出来。
for (const k of dynamicKeys.keys()) if (!(k in zh)) problems.push(`常量表推出但 zh_CN 缺键：${k}（跑一次 node scripts/i18n-keys.mjs --write）`);
```

**这道门当场就红了** —— 13 个新键还没进词表，它一条条列了出来：

```
✘ 13 项问题：
   · 常量表推出但 zh_CN 缺键：shortcut.nav（跑一次 node scripts/i18n-keys.mjs --write）
   · 常量表推出但 zh_CN 缺键：shortcut.edit …
```

这正是要的：**新写的门要立刻见到它红一次**，否则不知道它通没通电。

### 23.4 ★ 顺出来的缺口二：门装错了顺序 → 假红

`check` 原本的顺序是：

```
gen-style → tsc → typecheck:tests → lint:tests → i18n:check → tests/run → build → smoke
```

而第四道校验（「根目录 `i18n/` 产物必须跟上真源」）当时挂在 `i18n:keys --verify` 里，
也就是**排在 `build` 前面**。后果是：刚改完真源、还没构建时，`npm run check` 必然报红。

这是**假红**。而假红的危害和 22.6 那个「假绿」是同一件事的两面：
**门给错信号，人就会学会忽略它。** 一个每次改文案都亮红的门，三天之内就会变成
「哦那个红是正常的」。

所以把它拆出来单独成 `--built` 模式，挪到 `build` 之后：

```
gen-style → tsc → typecheck:tests → lint:tests → i18n:check → tests/run → build → i18n:built → smoke
```

```json
"i18n:keys":  "node scripts/i18n-keys.mjs --verify",
"i18n:built": "node scripts/i18n-keys.mjs --built",
"i18n:check": "npm run i18n:audit && npm run i18n:keys"
```

顺手把它从「只比键集合」升级成**连值一起比** —— 22.6 那个坑的失败形态就是
「键还在、值过期」，只比键集合会漏掉：

```
✘ 2 项问题：
   · 根目录 i18n/zh_CN.json 是构建产物且已过期：产物缺 13 键（如 shortcut.clip）—— 跑一次 npm run build
   · 根目录 i18n/en_US.json 是构建产物且已过期：产物缺 13 键（如 shortcut.clip）—— 跑一次 npm run build
```

顺带修了两处**措辞**上的同类隐患 —— 脚本日志和探针注释里都写着 `i18n/zh_CN.json`，
而实际该动的是 `src/i18n/zh_CN.json`。路径写错在日志里，就会有人照着去改产物，
然后下一次 build 把它覆盖掉 —— 又是「文案改了死活不变」。

> **门的三个失效模式，这一步一次见全了**：装错位置（假绿）、查错对象（动态键漏网）、
> 挂错顺序（假红）。它们都不表现为「报错」，而表现为「报错报得不对」——
> 比没有校验更难发现，因为它给的是结论，不是疑问。

### 23.5 能红对照补到第五条通路

原有探针覆盖四条注入通路。快捷键弹层是**第五条** —— 它虽然也读 `this.i18n`，
但**渲染路径完全不同**：前四条是「DOM 属性 / 元素文本直接取值」，
这一条是「模块级常量表 `map` → `join` → `showMessage` 弹层」。

这类路径的失败形态很特别：**键在词表里，但没人读它。**
静态校验全绿（键存在）、前四条通路全绿（别的路径接上了），
只有这一条静默显示中文。

补进 `probe-i18n-render.mjs` 第 ⑤ 段（打开插件菜单 → 设置 → 点「查看快捷键」→ 读 `.b3-snackbar__content`）。

**能红对照**：临时把消费点改成绕过词表（`SHORTCUT_HELP.map(([, zh]) => zh).join("\n")`），
构建部署后跑探针：

```
带「【i18n探针】」标记的文案 5 / 21 条
    ✔ 逻辑结构图【i18n探针】     ← ①~④ 依旧全绿
    …
✘ 工具条那条通路通了，但快捷键弹层一条都没命中 —— 它的取值路径是独立的，得单独接
真实退出码 = 1
```

**只红第 ⑤ 条、①~④ 全绿** —— 说明这条检查确实独立生效，而不是蹭了别的通路的绿灯。
另外单独确认了**退出码是 1**（不是只打印红字）：
一个「打印红但 `exit 0`」的门，在 `&&` 链里等于不存在。

### 23.6 空行分隔：静态校验照不到的排版回归

`SHORTCUT_HELP` 里有一行 `["", ""]`，用来隔开「图内」与「全局」两组。
取值走的是 `zh ? this.t(key, zh) : ""` 这条分支 —— 空行一旦被丢掉，
两组会**粘在一起**：排版塌了，但不报错，静态校验也照不到（键、值、行数全都对）。

所以探针里加了一条排版断言：

```js
const gapKept = /\n\s*\n/.test(helpText);
```

结果：`空行分隔 保留`。这类「结构而非文案」的东西，只能靠渲染层看。

### 23.8 一个不在本次范围、但该记下来的发现

`shortcut.global` 那行写的是 **`⌥⌘D` / `⌥⌘V`** —— 这是 macOS 的修饰键字形。
在 Windows / Linux 上它是错的（本机就是 Windows）。

它不属于 i18n 的问题（不是「该不该翻」，而是「内容对不对」），所以本次没有动。
但它是真问题，记在这里：

- 思源自己展示快捷键时会按平台换算，插件把字形硬编码进说明文字里就绕过了那层换算；
- 而且这两条是**全局命令**，默认键位由思源分配，插件并没有写死 `customHotkey` ——
  也就是说插件其实**不知道**真实绑定是什么。

建议的修法（待确认，不擅自改）：把那行改成不写具体修饰键的表述，
例如「全局快捷键：把光标所在的列表切换为导图 / 大纲 · 并排面板打开导图
（默认键位见「设置 → 快捷键」，可自行修改）」。这样既跨平台正确，
也不会在用户改过键位之后给出过期信息。

### 23.9 教训

1. **最容易的那块，也可能藏着最值得写的问题。** 「单一常量、一个消费点」看起来
   没有技术含量，但它牵出了两条校验缺口和一条没被覆盖的渲染通路。
2. **下标键是一种会静默错位的设计。** 凡是「位置决定语义」的键，
   在可重排的列表上都该换成语义键 —— 代价是多打几个字符，收益是错位不可能发生。
3. **加新校验时，立刻让它红一次。** 没红过的门不算门。这一次两个新门都是
   在实现过程中就当场见到了红 —— 那不是意外，是设计。
4. **假红和假绿一样有害。** 校验要挂在**它真正成立的那个时刻**。
   一个每次改文案都亮红的门，三天内就会变成「哦那个红是正常的」。
5. **`exit` 码要单独确认。** 「打印红字但退出码 0」的门，在 `&&` 链里等于不存在 ——
   而管道（`| tail`）会把上游退出码吞掉，所以验证退出码必须绕开管道。
6. **排版也是行为。** 空行分隔、分组、顺序 —— 这些静态校验照不到的东西，
   只能在渲染层验，而且值得单独写一条断言。

## 二十四、把 23.8 那条遗留发现做掉：`⌥⌘D` 在 Windows 上到底该写什么

第二十三节结尾记了一条「不在本次范围、但该记下来」的发现：快捷键速查里写着
`⌥⌘D` / `⌥⌘V`，而本机是 Windows。当时说「待确认，不擅自改」。

这一节就是把它做掉。过程比预想的曲折 —— 而且**最有价值的部分不是改文案，
是中间那句「先量再改」量出来的东西**。

### 24.1 先量第一步：插件到底绑了什么

改之前得先确认这不是「文案写错了」，而是「文案和绑定到底是什么关系」。
读 `src/index.ts` 的命令注册：

```ts
this.addCommand({ langKey: "toggleMindMap",  hotkey: "⌥⌘D", callback: … });
this.addCommand({ langKey: "toggleSidePanel", hotkey: "⌥⌘V", callback: … });
```

插件**确实显式绑定了** `⌥⌘D` / `⌥⌘V`，而且注释里写着这两个键是当初对照
工作空间 `conf.json` 的 keymap 全表筛出来的（`⌥⌘M` 被「插入备注」占了、
`⌥⌘L` / `⌥⌘P` / `⌥⌘N` / `⌥⌘O` 被别的插件占了）。所以这不是随手写的值。

顺手把 `probe-i18n-command.mjs`（原本只查命令名）扩了一段，把
`os` / `platform` / `hotkey` / `customHotkey` / keymap 里实际生效的那条一起 dump：

```json
{ "os": "windows", "platform": "Win32",
  "commands": [
    { "langKey": "toggleMindMap",  "hotkey": "⌥⌘D", "customHotkey": "⌥⌘D", "inKeymap": null },
    { "langKey": "toggleSidePanel","hotkey": "⌥⌘V", "customHotkey": "⌥⌘V", "inKeymap": null } ],
  "keymapHits": [] }
```

`inKeymap: null` 说明用户没改过，生效的就是插件声明的默认值。

### 24.2 先量第二步：Windows 上实际按什么键

`diag-commands.mjs` 里早就写着答案 —— 它发的是 **Ctrl+Alt**：

```js
const hotkey = (page, key) => combo(page, key, { ctrl: true, alt: true });
```

而这一支在 `ux:all` 里是绿的（按 Ctrl+Alt+D 确实切换了导图、写了内核属性，
还有「导图有焦点时全局键不能被吃掉」的回归断言）。所以 Windows 上
`⌥⌘` 被思源解析成 **Ctrl+Alt**。

### 24.3 ★ 决定性证据：思源自己把 `⌥⌘X` 显示成什么

到这里还只是「行为上等价于 Ctrl+Alt」，但**该写什么文案**取决于另一件事：
思源在自己的界面上怎么显示这套键位？如果思源也显示 `⌥⌘D`，那插件与思源一致，
顶多是「思源的约定与操作系统约定不同」；如果思源显示 `Ctrl+Alt+D`，
那插件就是在用一套用户在自己设置页里找不到的符号 —— 属于真错。

写了个只读探针 `probe-keymap-display.mjs` 去问。答案来了两次：

**第一次，从主菜单白捡的**（这条最有意思 —— 本来只是要点「设置」，菜单项
文本里却连着键位）：

```
设置Alt+P        魔法排版Ctrl+Alt+P        FlowMindCtrl+Alt+L       反向链接Alt+7
```

`魔法排版` / `FlowMind` 的键位在 `conf.json` 里存的正是 `⌥⌘P` / `⌥⌘L`，
「设置」对应 `⌥P`。**思源把 `⌥⌘P` 显示成了 `Ctrl+Alt+P`。**

**第二次，打开思源自己的「设置 → 快捷键」页**：

```
主菜单     Alt+\            命令面板   Shift+Alt+P     只读模式   Ctrl+Shift+G
聚焦到上层 Alt+←            聚焦       Alt+→          前进       Ctrl+]
新建文档   Ctrl+N           搜索       Ctrl+P         全局搜索   Ctrl+F
固定搜索   Ctrl+Shift+F     替换       Ctrl+R
```

结论封闭：**思源在 Windows 上到处都把 `⌥⌘X` 换算成 `Ctrl+Alt+X`。**
插件写死 `⌥⌘D` 确实是在用一套用户在思源里看不到的符号。

### 24.4 ★ 顺出来的一条：规范顺序是 Ctrl → Shift → Alt

上面那张表不止回答了「换算不换算」，还回答了「**怎么排**」。把 keymap 原值和
显示值对照：

| keymap 原值 | 思源显示 | 推出 |
| --- | --- | --- |
| `⌥⌘P`（魔法排版） | `Ctrl+Alt+P` | Ctrl 在 Alt 前 |
| `⇧⌘F`（固定搜索） | `Ctrl+Shift+F` | Ctrl 在 Shift 前 |
| `⌥⇧P`（命令面板） | **`Shift+Alt+P`** | **Shift 在 Alt 前** |

三条合起来是 **Ctrl → Shift → Alt → 主键**。

我第一版实现排的是 `Ctrl → Alt → Shift` —— 对 `⌥⇧X` 组合会排错。
**而更要命的是：我把这个错的顺序写进单测断言住了。**

```
eq(readableHotkey("⌥⇧↓", false), "Alt+Shift+↓", "带方向键主键的组合同样成立");
```

这条断言是绿的 —— 因为它断的就是我自己的错误实现。**一个把错行为锁住的测试，
比没有测试更糟**：它把「看起来验过了」和「验对了」混成了一件事。

> 如果不是顺手把思源设置页那 12 行读下来，这个错会一直躺在那里，
> 并且带着一条绿色的断言。**「量一下」的收益往往不在你本来想问的那个问题上。**

### 24.5 改法：让声明和文案共用同一份数据

只改文案是不够的 —— 真正的隐患是「声明了一个值、文案里又写了一遍」，
下次改绑定就会漂移。所以：

**① 默认键位提成模块级常量，两处共用。**

```ts
/**
 * ⚠️ 声明（`addCommand` 的 `hotkey`）与说明文字（快捷键速查）必须**共用这两个常量**。
 * 分开写迟早会漂移：改了绑定忘了改说明，用户按文档去按、按不动。
 */
const HOTKEY_TOGGLE = "⌥⌘D";
const HOTKEY_SIDE = "⌥⌘V";
```

`addCommand({ hotkey: HOTKEY_TOGGLE })`，说明文字也从它渲染。

**② 换算做成纯函数，单独成模块**（`src/utils/hotkey.ts`）：

```ts
export function readableHotkey(hotkey: string, isMac: boolean): string {
    if (!hotkey) return "";
    if (isMac) return hotkey;
    const parts: string[] = [];
    if (/[⌘⌃]/.test(hotkey)) parts.push("Ctrl");
    if (hotkey.includes("⇧")) parts.push("Shift");
    if (hotkey.includes("⌥")) parts.push("Alt");
    const key = hotkey.replace(/[⌘⌥⇧⌃]/g, "");
    if (key) parts.push(key);
    return parts.join("+");
}
```

`isMac` 作为**参数**传入而不是在函数里读全局 —— 读全局的话测试就只能在某一台
机器上跑，另一个平台的分支永远验不到。

**③ 词表那条改成占位符模板**（复用第二十二节做的 `t(key, fallback, vars)`）：

```json
"shortcut.global": "{toggle} 把光标所在的列表切换为导图 / 大纲 · {side} 并排面板打开导图"
```

```ts
private shortcutHelp(): string {
    const vars = {
        toggle: readableHotkey(HOTKEY_TOGGLE, isMacPlatform()),
        side: readableHotkey(HOTKEY_SIDE, isMacPlatform()),
    };
    return SHORTCUT_HELP.map(([key, zh]) => (zh ? this.t(key, zh, vars) : "")).join("\n");
}
```

**为什么不做成「中英各两套（mac / win）」**：词表是按语言分的，加平台维度会让
键数翻倍，而且 `--verify` 的「中英键集合一致」也跟着复杂。占位符把平台维度
从词表里拿出去，交给代码算 —— 词表只管语言，代码只管平台，各管一件事。

### 24.6 验证

**单测**（`tests/entry.ts` 第 13 节，312 条断言，比上一步 +14）：

```
[13] 键位换算：思源表示法 → 平台可读写法
```

覆盖：macOS 原样保留、Windows 三条修饰键、**顺序三条**（各自引了思源实测证据）、
主键不被吞掉（`F2` / `⌘\`）、空串（迁移命令故意不绑键，不能变成 `Ctrl+`）、
幂等（换算过的串再算一次不变样）。

**真机**（`diag-settings.mjs` 加了一条平台一致性断言，36 项全过）：

```
✓ ★ 全局键位的写法与平台一致（Windows 上必须是 Ctrl+Alt+D / Ctrl+Alt+V，整段不出现 ⌥）
   os=win/linux｜全局行含 ⌥⌘: false｜含 Ctrl+Alt: true｜整段含 ⌥: false
   「Ctrl+Alt+D 把光标所在的列表切换为导图 / 大纲 · Ctrl+Alt+V 并排面板打开导图」
```

**能红对照**：把 `readableHotkey` 改成原样返回（等价于「忘了换算」）→

```
✗ ★ 全局键位的写法与平台一致
   os=win/linux｜全局行含 ⌥⌘: true｜含 Ctrl+Alt: false｜整段含 ⌥: true
   「⌥⌘D 把光标所在的列表切换为导图 / 大纲 · ⌥⌘V 并排面板打开导图」
```

**一次假红，值得单独记**：这条断言第一版是对**整段弹层**扫 `/[⌥⌘]/`，
结果被判红 —— 因为另一行写着「聚焦：Ctrl/⌘ + 双击节点」。那行是**故意的
跨平台写法**（两种都给出），本身没问题，是我的正则太宽：

- `[⌥⌘]` 是**字符类**，匹配任意单个 `⌘` 或 `⌥`，不是「`⌥⌘` 这个两字符序列」；
- 而且 `⌘` 在「Ctrl/⌘」这类跨平台写法里是合法的，不该一概禁掉。

修法：断言**收窄到全局那一行**，并且只禁 `⌥`（`⌥` 在 Windows 上没有合法用途）。
**把断言改宽之前要分清「是代码错了」还是「是测试写错了」** —— 前者要改代码，
后者要改测试，两者不能混。

**一类例外：插件自己判的修饰键，两种写法都是真的。**

`shortcut.focus` 那行写的是「Ctrl/⌘ + 双击节点」—— 它**故意同时给出两种**，
而且这是准确的：`renderer.ts` 里双击聚焦的判断是

```ts
if ((e.ctrlKey || e.metaKey) && n.children.length > 0) { … }
```

**两种修饰键在任何平台上都接受**（`metaKey` 在 Windows 上对应 Win 键，但用户按不到，
所以实际等价于「Ctrl 或 ⌘ 都能用」）。所以这行的斜杠写法不是漏改，是正确写法。

区别在这里：

| 类别 | 例子 | 该写什么 |
| --- | --- | --- |
| **思源的键位串**（绑定） | `⌥⌘D` | 必须按平台换算成 `Ctrl+Alt+D` |
| **插件自己判的修饰键**（运行时） | `e.ctrlKey \|\| e.metaKey` | `Ctrl/⌘` 同时给出，本来就都对 |

这条值得写下来，否则后来人会看到「有的行换算了、有的行没换算」，把它当不一致去「修」。

### 24.7 教训

1. **「待确认」的发现，确认完再改，往往比直接改收获大。** 这条一开始看着就是
   「文案写错了」，量完才发现：绑定是对的、行为是对的、错的只是**写法与用户
   所见不一致** —— 而修法也随之变了（不是改文案，是让声明和文案共用数据）。
2. **答案常在旁边。** 思源显示规则的决定性证据，一半是从「点设置时菜单项文本
   里连着键位」白捡的；另一半来自顺手打开的一个设置页。**本来只想问一个问题，
   顺手多读了一屏。**
3. **★★ 把错行为锁进测试，比不测更糟。** 我第一版排错了修饰键顺序，
   还给它配了一条绿断言 —— 于是「验过了」和「验对了」被混成一件事。
   测试的价值取决于它断的是**谁的行为**：断的是需求，还是断的是我的实现。
4. **引用证据时把证据一起写进注释。** 那三条顺序断言各自标了它对齐的是思源
   哪一行（`魔法排版 Ctrl+Alt+P` / `固定搜索 Ctrl+Shift+F` / `命令面板 Shift+Alt+P`）——
   下次有人觉得顺序不对，能直接去核，而不是重推一遍。
5. **维度该分层，不该平铺。** 平台维度放进词表会让键数翻倍、校验复杂；
   放进代码算一次就好。**词表管语言，代码管平台。**
6. **正则的字符类很容易写成你以为的序列。** `[⌥⌘]` 不是 `⌥⌘`。
   这类错在断言里会表现成「莫名其妙的假红」，而假红多了就会被忽略。

## 二十五、上架前审查：按集市的要求逐条核，而不是按「我觉得没问题」

### 25.1 起因

功能面收口了，下一个里程碑是**上架**。上架和前面的所有工作有个根本区别：

> 前面每一轮都是「我认为它该怎样」，上架是「**别人拿一把尺子来量**」。

所以这一节不写新功能，只做一件事：把集市的**硬要求**逐条列出来，逐条核。
核的方式不是「读一遍代码觉得对」，而是**能量数字的量数字、能跑真机的跑真机**。

### 25.2 集市对「仓库」的要求 —— 这些不在 `plugin.json` 里，但漏了就拿不到包

`plugin.json` 只描述**包**，不描述**仓库**。而集市有一部分要求是关于仓库的：

| 要求 | 出处 | 状态 |
| --- | --- | --- |
| 仓库名必须与 `plugin.json` 的 `name` **完全一致** | plugin-sample「Get started」 | ⚠️ 待用户建仓时遵守 |
| 默认分支必须是 `main` | 同上 | ⚠️ 同上 |
| 必须发 **GitHub Release**，把 `package.zip` 作为**二进制附件** | 「List on the marketplace」 | ⚠️ 待用户操作 |
| 首次上架：fork `bazaar`，往根目录 `plugins.txt` 加一行 `owner/repo`，PR 到 `main` | 同上 | ⚠️ 待用户操作 |
| 后续更新：只需升 `version` + 发含 `package.zip` 的 Release，**不用再提 PR** | 同上 | — |

**最容易被忽略的是第三条。** 集市拉的是 **Release 里的 `package.zip`**，
不是仓库里的源码 —— 也就是说：

> **只 push 代码、不发 Release，集市上是拿不到包的。**
> 而这件事在本地怎么测都测不出来：本地 `npm run package` 会生成 `package.zip`，
> `npm run deploy` 会把它拷进工作空间，一切看起来都正常。

这条写进了两份 README 的上架 TODO（第 2 节），因为它是「本地全绿、线上拿不到」的典型。

### 25.3 `package.zip` 逐条核对

规范要求包**至少**包含：`plugin.json` / `index.js` / `index.css` / `README*.md`，
声明了 `icon` / `preview` 的话还要有对应图片，多语言插件要有 `i18n/*`。

实际产物（`npm run package`，10 个文件，压缩后 136.1 KB）：

| 文件 | 大小 | 规范要求 | 结论 |
| --- | --- | --- | --- |
| `plugin.json` | 820 B | 必需 | ✅ |
| `index.js` | 203 064 B | 必需 | ✅ |
| `index.css` | 50 800 B | 必需 | ✅ |
| `README.md` | 11 250 B | 必需 | ✅ |
| `README_zh_CN.md` | 32 415 B | 必需 | ✅ |
| `i18n/zh_CN.json` | 17 538 B | 多语言插件必需 | ✅ |
| `i18n/en_US.json` | 18 418 B | 同上 | ✅ |
| `icon.png` | 4 479 B（**4 KiB**） | ≤ 64 KiB，推荐 160×160 | ✅ **160×160** |
| `preview.png` | 29 533 B（**28 KiB**） | ≤ 512 KiB，推荐 1024×768 | ✅ **1024×768** |
| `LICENSE` | 1 086 B | 规范未提，多余但无害 | ✅ |

顺带核出两条规范里写着、但很容易踩的：

- **不支持 SVG**（`icon` / `preview` 只收 PNG / JPEG / WebP / AVIF）；
- **空值无效** —— 想不放图就**删掉整个字段**，写 `""` 会被判无效。

### 25.4 `minAppVersion`：从「拍的 3.1.0」改成「有据的 3.6.4」

`plugin.json` 里原来写的是 `"minAppVersion": "3.1.0"`。

**这个值是怎么来的？—— 拍的。** 没有任何依据，就是「看着差不多」。

正确的做法不是猜一个更保守的数，而是**推导**：

> 把插件实际用到的内核 API 列出来 → 查每个 API 的**引入版本** → 取最大值。

挨个查下来，真正带版本门槛的只有**一个**：

```
/api/block/batchUpdateTaskListItemMarker
  → PR #17461「Add kernel API /api/block/batchUpdateTaskListItemMarker」
  → 2026-04-11 合入 dev
  → milestone: 3.6.4（2026-04-14 closed）
```

其余用到的（`foldBlock` / `unfoldBlock` / `updateTaskListItemMarker` /
`getPathByID` / `sql` 等）都是更早就有的老接口，门槛低于它。

所以 `minAppVersion` 改成 **`3.6.4`** —— 这个数**能追到一条 PR、一个 milestone**。

#### 怎么查「某个 API 从哪个版本开始有」

踩到的坑：**release note 里查不到。** 我先把近 100 个 Release 的 body 全捞下来
grep `batchUpdateTaskListItemMarker`，**零命中** —— 因为思源的 Release body 基本只挂
更新日志的链接，不列 API 变更明细。

有效路径是**直接问 PR 的 milestone**：

```
GET https://api.github.com/repos/siyuan-note/siyuan/pulls/17461
  → .milestone.title = "3.6.4"
  → .milestone.closed_at = "2026-04-14T01:29:03Z"
```

即「**找引入它的那个 PR，问 PR 的 milestone**」，而不是找 Release 说明。
这条记下来，下次给别的插件定 `minAppVersion` 可以直接复用。

#### 还剩一个需要用户拍板的选择

| 选项 | 放行范围 | 依据强度 |
| --- | --- | --- |
| `3.6.4` | 更多用户 | 能追到 PR + milestone（**推导**） |
| `3.8.4` | 只放行实测过的版本 | 本机就是这个版本（**实测**） |

按第二十四节那张「期望值来源可信度」表，实测比推导硬。
但这里两者**不冲突**：`3.6.4` 是「API 存不存在」的下界（硬事实），
`3.8.4` 是「我测过没有」的下界（覆盖度问题）。
所以推荐 `3.6.4`，并把「只在 3.8.4 上实测过」如实写进 README。

### 25.5 `frontends: ["all"]` 是诚实的吗 —— 拿真机移动端量

`plugin.json` 里声明了：

```json
"backends": ["all"],
"frontends": ["all"]
```

`frontends: ["all"]` 等于对集市说「桌面端、桌面窗口、移动端、浏览器桌面端、
浏览器移动端**都能用**」。这是个**承诺**，而承诺是可以不成立的。

**为什么必须测真正的移动端前端**：思源的移动端 App 走的是**另一套前端构建**
（`/stage/build/mobile/`），DOM 结构、工具栏、事件模型都不一样。
在桌面端把窗口调窄，测的是「桌面端在窄屏下的表现」，
跟 `frontends: ["mobile"]` 这句声明**不是一回事**。

于是写了 `probe-mobile-touch.mjs`：用 CDP 切到移动端前端 + 390×844 dpr3 +
`Emulation.setDeviceMetricsOverride({mobile:true})` + 触摸仿真，覆盖：

| 段 | 测什么 |
| --- | --- |
| A | 插件在移动端前端能装载 |
| B | 导图能渲染出来 |
| C | 350px 窄屏不横向溢出 |
| D | 按钮热区够大（最小 29×24px） |
| E | 触摸选择 + 操作条 + 复选框写内核 |
| F | 长按出菜单 |
| G | 拖动平移 |
| H | 无控制台错误 |

**结果：15/15 通过。** 结论：`frontends: ["all"]` 这句是**诚实的**。

#### 顺带排掉一个「看起来像 bug」的假象

D 段一开始报「过滤 chip 尺寸 0×0」—— 看着像布局塌了。追下去发现是
**fixture 造的假象**：那份 fixture 是无序列表、**没有待办**，
而过滤 chip 按设计会自动收起。改用任务列表 + 只量**可见**按钮后，全部达标。

E 段更绕：「点节点中心选中 0 个」。原因是**点复选框会切换待办 → 写内核 → 重渲染**，
于是 `.mm-node` 元素被换掉、盒子尺寸也变（43px → 87px）——
表现成「同一个元素两次点击结果不同」，看起来像 bug，其实是**测的是移动靶**。

干净的量法是用**无序列表**（点哪儿都不改文档）单写一支 `probe-mobile-tap.mjs`：
点节点中心 **8/8** 命中、点文字中心 **4/4** 命中 → **无产品 bug**。
探针改为按元素类型分别断言，并把「点复选框会切换待办」变成一条**正断言**
（读**内核 kramdown**，不看 DOM —— DOM 会重渲染，内核不会骗人）。

### 25.6 顺出来的第三件事：19 支「无家可归」的脚本

登记新探针时想手算一下「哪些还没名字」，算完发现**远不止新加的三支**。
既然这是个「人会反复忘」的问题，就该**变成门**，而不是再手算一遍。

#### 判据

> **要么被 `package.json` 引用（有名字），要么被别的文件 `import`（是共享助手）；
> 两者都不是 = 孤儿。**

**为什么不是「必须进套件」**：第十九节已经修正过这条 ——
该长期有效的**断言**不进套件 = 必然腐烂；**一次性探针**不进套件没问题
（给它加门反而是造一扇永远红的门），但它**至少得有个名字**，
否则下次想重跑都找不到它。所以这道门只问「有没有名字 / 是不是助手」。

#### 门加在哪

加在 `scripts/lint-tests.mjs` 的**第三道校验**（原来是两道：语法解析、相对 import）。
选它的理由和原来那两道一样：**静态、毫秒级、已在 `npm run check` 里**。

#### 门红了 —— 21 支，比我手算的多

按本项目自己的规矩（「新写的门要立刻见它红一次」），写完先跑一次：

```
    · 给它在 package.json 里起个名字（沿用 probe:* / ux:* 惯例）—— 它还有重跑的价值；
    · 删掉它 —— 问题已经回答完了，留着只会腐烂。
```

**真实退出码 1**（单独跑的，没走管道 —— `| tail` 会吞掉上游退出码）。

⚠️ **门比我手算多抓了 2 支，也少报 1 支误判**：

| | 范围 | 判据 | 结果 |
| --- | --- | --- | --- |
| 我手算 | 只圈 `tests/kernel/` | 「没在 package.json 里」 | 20 支，其中 `_doc-cleanup.mjs` **是助手，误报** |
| 门 | `tests/` + `scripts/` | 「没名字 **且** 不是助手」 | **21 支**真孤儿 |

多出来的 2 支在 `scripts/` 下，我压根没扫：`diag-kernel.mjs`（内核 API 探针）、
`i18n-apply.mjs`（i18n 抽取工具，配 `scripts/i18n-map.json`）—— 后者是个正经工具，
**从来没人给它起过名字**。

> **手算既会漏（范围圈窄了）也会多（判据不严）。** 这就是为什么值得写成门。

#### 门的自检：三个分支各验一次

绿了不代表门是对的 —— 也可能是门自己坏了。所以单独造三种情况：

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| 新建一支没人引用的脚本 | 红 | ✅ 报 1 处，退出码 1 |
| 新建一支**被 import** 的助手 | 不报 | ✅ 未出现 |
| 新建一支「没名字、也没人 import」的 | 红 | ✅ 报了，同时助手那支仍未出现 |

三分支全对，清掉自检文件，复跑转绿（退出码 0）。

⚠️ 另一支有门的 `probe-i18n-render` **没有**接进套件，因为它的用法第一步是
**手工改词表加标记**（否则中文环境下词表值和 fallback 同值，证明不了什么）。
**需要人工前置步骤的脚本不能当门** —— 它会变成一扇「跑了也说明不了问题」的门。

### 25.7 教训

1. **上架审查的尺子不在你手里。** 前面每一轮都是「我认为它该怎样」；
   上架是别人拿尺子来量。所以审查的动作应该是**把要求逐条列出来核对**，
   而不是「再读一遍代码觉得没问题」。
2. **`minAppVersion` 不能拍。** 它是「插件用到的 API 里最年轻的那个」的引入版本。
   查法是**找引入 API 的 PR、问 PR 的 milestone** —— Release body 里查不到
   （思源的 release note 只挂链接）。
3. **声明就是承诺，承诺要量。** `frontends: ["all"]` 是一句话，15/15 是一个证据。
   而量它必须用**真正的移动端前端** —— 「桌面端开窄窗口」测的不是同一件事。
4. **★★ 测出来的「bug」先问是不是测量本身的问题。** 这一轮两次假象
   （chip 0×0、点中心选不中）都不是产品 bug，一次是 fixture 缺待办、
   一次是「点复选框会重渲染」造成的移动靶。**追下去再下结论。**
5. **★★ 手算会同时漏和错。** 我手算 20 支（漏了 `scripts/` 的 2 支、误报 1 支助手），
   门算出 21 支。**「反复忘」的问题就该变成门**，手算一次只是把问题往后推。
6. **门要自检，不能只看它绿。** 绿可能是门坏了。三个分支各造一个用例，
   才是「这道门真的在守」的证据。这条和第十七节「能红对照」是同一个道理。
7. **需要人工前置步骤的脚本不能当门。** `probe-i18n-render` 有 3 处 `exitCode`、
   判定也是对的，但它的第一步得手工改词表 —— 接进套件只会得到一扇
   「跑了也说明不了问题」的门。**有判定 ≠ 能当门，还要问「能不能无人值守地跑」。**
8. **★★ 写进文档的「解释」也要核 —— 解释错了比没有解释更糟。**
   README 里给 `minAppVersion` 写理由时，我写的是「插件无条件调用
   `batchUpdateTaskListItemMarker`（勾选待办用的接口）」。复核代码才发现：
   **勾选单条待办走的是 `updateTaskListItemMarker`**（老接口，无版本门槛），
   `batch…` 是**批量勾选**（多选后一次性勾）才走的。
   门槛值 `3.6.4` 本身没错，**但理由是错的**。
   > 一个错的理由会被后来人当成依据 —— 它比「没写理由」危险得多，
   > 因为「没写」至少会让人去查。**写理由之前，先核理由。**

   顺带记一条可复用的判据：定 `minAppVersion` 要取的是
   **插件用到的所有内核接口里门槛最高的那个**，不是第一个想起来的那个。
